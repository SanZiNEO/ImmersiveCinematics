# 规则命令的服务端信任边界

> 状态：未实现
> 范围：规则动作 `emit_command` 的客户端→服务端请求身份、实例与观看者授权、命令来源、命令源权限、旧协议处置与验收
> 关联：`rule-system.md`、`rule-collection.md`、`rule-facts-scheduling.md`、`rule-implementation.md`、`track-event.md`；代码见 `trigger/network/C2SRuleCommandPacket.java`、`trigger/server/ScriptEventManager.java`、`util/SuccessOnlySource.java`、`trigger/network/C2SPlaybackStartedPacket.java`、`script/ScriptValidator.java`

## 一、摘要

规则动作 `emit_command` 让脚本在客户端条件成立时请求服务端执行命令。现行链路把客户端传来的命令原文交给权限 4 的命令源，只检查发送者是否在该播放实例的观看者集合；观看者集合又可由客户端播放回执自行登记。结果是任意能发送模组 C2S 包的客户端（包括修改过的模组客户端）只要知道一个已加载脚本的 id，就能把自己变成观看者，并以 op 权限执行任意命令。

本文把这条链路改成服务端权威：客户端只提交脚本内动作的引用，服务端按脚本定义解析命令；观看者身份由服务端在发播放包时签发，客户端回执不能自证；规则命令使用受限命令源，EVENT 轨的服务端命令不受影响。状态未实现。

## 二、为什么做

### 2.1 问题

- 客户端请求携带命令原文，服务端没有把请求与脚本中定义的 `emit_command` 动作做比对。
- 服务端唯一检查是“发送者是否在该实例的观看者集合”，但观看者身份由客户端播放回执登记；客户端可以伪造 `started=true` 把自己加入任意已加载脚本的观看者集合。
- 命令执行使用权限 4 的命令源；因此“能看脚本”实际等于“能以 op 权限执行任意命令”，而不是“只能执行作者写好的命令”。
- 校验器只检查 `emit_command.command` 是非空字符串；它不限制命令内容，而且伪造的网络包不经过校验器。
- 现有注释把观看者检查称为“防命令注入”，但它只把注入面从“能发模组 C2S 包的客户端”缩小到观看者；观看者不是权限主体，身份也可以伪造。
- EVENT 轨的权限 4 不属于本条问题：EVENT 命令由服务端事件时间线触发，没有客户端命令请求。问题在规则命令复用了同一条“客户端请求→权限 4”的路径。

现状依据：`C2SRuleCommandPacket` 携带 `command` 原文；`ScriptEventManager.handleRuleCommand` 只调用 `isRuleCommandAllowed` 后执行；`SuccessOnlySource` 构造权限为 4；`C2SPlaybackStartedPacket` 的 `started` 由客户端传入并直接进入播放账本；`ScriptValidator.checkActionEmitCommand` 只检查非空字符串。

### 2.2 目标

- 客户端请求不再包含命令原文；只包含服务端可解析的脚本动作引用。
- 服务端按脚本定义解析该动作，确认类型是 `emit_command`，取服务端侧命令字符串；未知动作、非命令动作、悬空引用一律拒绝。
- 观看者/实例授权由服务端在发送播放包时签发；客户端播放回执只能确认“已开始”，不能新增观看者或新建实例。
- 规则命令使用受限命令源，默认权限不高于 2；EVENT 轨继续使用权限 4；服务端配置可以整体调整规则命令上限，脚本不能自行提高。
- 旧的客户端原文命令协议不再保留；旧请求按协议错误丢弃，不回退到原文执行。
- 可观察的验收结果：伪造播放回执不产生观看者；伪造动作引用不执行命令；合法请求只执行脚本定义的命令；默认无法通过 `emit_command` 执行权限 3/4 的命令；EVENT 命令仍按原权限执行。

### 2.3 非目标

- 不做通用权限/ACL 系统；本文只收紧 `emit_command` 这一条客户端→服务端命令链路。
- 不在服务端重新判定客户端规则条件。规则条件、触发时机仍由客户端求值；服务端不证明“规则真的成立”，只保证客户端不能引入脚本外命令。
- 不改变 EVENT/MOD_EVENT 的命令协议、事件身份、去重与权限 4 口径。
- 不把脚本作者当攻击者；脚本文件仍属于服务端信任域。作者在 `emit_command` 里写危险命令，仍由作者与服务器运营者负责，本文只提供权限上限和审计。
- 不改造编辑器本地服务的 Origin/token 防护；本地预览不参与服务端播放账本。
- 不定义规则集合的稳定绑定身份、序列化字段或引用形式；这些仍归 `rule-collection.md` 的结构评审。本文只要求请求能唯一定位到脚本内的 `emit_command` 动作。

## 三、方案

### 3.1 作者面

作者仍然在脚本里写 `emit_command` 和命令原文；编辑器、脚本格式和校验入口不需要因此改成“选择命令白名单”。作者写的是“脚本定义”，不是“客户端请求”。

运行时行为改变：

- 规则在客户端触发时，客户端只告诉服务端“执行这个实例里的这个动作”，不再把命令字符串发给服务端。
- 服务端从自己加载的脚本里取出该动作的命令原文，按脚本作者的意图执行。
- 如果动作引用无效、动作不是 `emit_command`、实例没有授权，请求被丢弃；不会退回执行客户端传来的任何文本。

### 3.2 观看者与实例

- 服务端在发送播放包时登记本次实例的目标玩家；这份登记就是观看者授权的来源。
- 实例 id 由服务端生成并随播放包下发；客户端不能用一个自造的实例 id 获得授权。
- 客户端播放回执只确认“该玩家确实开始播放”；只有已经在目标名单里的玩家才能进入播放账本。回执里的 `started=true` 不再是观看者的创建入口。
- 本地预览、无服务端实例的播放不发送规则命令；需要验证命令时走正式播放。

### 3.3 命令源权限

- EVENT 轨继续使用权限 4 的命令源：命令由服务端事件时间线触发，脚本属于服务端信任域。
- 规则命令使用独立的受限命令源：保留玩家身份、成功结果回执和失败日志，但权限由服务端配置决定，默认 2。
- 默认上限下，`/op`、`/stop`、`/kick` 这类权限 3/4 的命令不会通过 `emit_command` 执行；作者需要这类能力时，改用服务端触发器/EVENT，或由服务器运营者显式提高规则命令上限。
- 脚本不能声明自己的权限等级；权限只由服务端配置决定，避免脚本作者绕过上限。

### 3.4 失败与旧协议

- 未知实例、非观看者、未知动作、非 `emit_command` 动作、空命令：丢弃请求并限频记录；不中断播放，不执行部分命令。
- 旧 `C2SRuleCommandPacket` 的原文命令协议不再注册/处理；旧客户端请求按协议错误丢弃。不做双读或兼容回落。
- 规则命令请求做每玩家/每实例的频率限制；超限丢弃并记录。阈值属于服务端配置，不影响正常规则频率。

## 四、技术细节

### 4.1 核心模型

- **规则命令请求（RuleCommandRequest）**：客户端→服务端的请求，字段只包含脚本 id、实例 id、动作引用，可选执行身份；不包含命令原文。
- **规则命令动作（RuleCommandAction）**：服务端在解析期从脚本定义编译出的动作表项，保存 `emit_command` 的命令原文、动作路径与来源；命令原文只存在于服务端。
- **播放授权（PlaybackGrant）**：服务端在发送播放包时创建的实例授权，保存 `(scriptId, instanceId)` 的目标玩家集合与生命周期；它是观看者身份的唯一来源。
- **规则命令源（RuleCommandSource）**：带玩家身份与受限权限的命令源；成功结果回执，失败进入限频日志。
- **规则命令审计（RuleCommandAudit）**：记录被拒绝的请求、实际执行的动作与权限结果；用于运营排查，不参与判定。

信任模型：

| 对象 | 是否可信 | 说明 |
|---|---|---|
| 客户端网络包 | 不可信 | 可伪造实例 id、动作引用、播放回执与字段值 |
| 客户端规则条件/时机 | 不可信（仅用于请求） | 服务端不证明条件成立；只限制请求能引用什么 |
| 服务端脚本文件 | 可信 | 命令原文、动作定义、规则结构来自服务端加载的脚本 |
| 服务端播放授权 | 可信 | 由发送播放包的路径创建，不由客户端回执创建 |
| 服务端命令调度器 | 可信 | 最终执行权限与命令解析由服务端决定 |

### 4.2 契约

- **授权创建**：服务端向目标玩家发送播放包时创建 `PlaybackGrant`；目标集合来自发送路径（单人、全体、除触发者等），实例 id 由服务端生成。
- **授权消费**：客户端播放回执只有在玩家已在该 grant 中时才允许进入播放账本；回执不能新增目标，也不能创建新实例。未回执的授权不产生观看者。
- **请求校验**：处理规则命令请求时，依次检查实例存在、玩家在该实例 grant 与播放账本中、动作引用可解析、动作类型为 `emit_command`。任一失败即拒绝。
- **动作解析**：服务端从脚本定义取命令原文；客户端请求中的任何命令文本字段都不存在，或被显式忽略。不得用客户端文本回退。
- **执行**：命令按脚本定义拆分 `&&`，每段使用 `RuleCommandSource` 执行；命令失败不中断播放，失败原因限频记录。
- **权限**：规则命令源权限 = 服务端配置上限，默认 2；EVENT 轨仍为 4；脚本不能覆盖。超过上限的命令由命令调度器拒绝。
- **生命周期**：实例结束、停播、脚本替换、玩家退出时撤销对应 grant 与账本；动作表随脚本加载/替换重建，旧动作引用失效；撤销后的请求一律拒绝。
- **旧协议**：原文命令包不再注册；旧请求不进入 `handleRuleCommand` 的兼容分支。
- **本地预览**：没有服务端 grant，不发送规则命令；预览可以显示动作，但不执行服务端命令。
- **频率限制**：按玩家/实例/动作限制请求频率；超限丢弃并记录，不排队补执行。

验收口径：

- 伪造 `started=true` 的播放回执，不增加观看者，后续规则命令被拒。
- 伪造不存在的动作引用或非 `emit_command` 动作，不执行任何命令。
- 合法观看者对合法动作的请求，只执行脚本中该动作的命令，不执行请求里的其它文本。
- 默认配置下，`emit_command` 不能执行权限 3/4 的命令；EVENT 命令仍可执行。
- 跨实例引用被拒；实例结束后再请求被拒。
- 旧原文命令包被丢弃，不回退执行。

### 4.3 数据形态

- 请求只存脚本 id、实例 id、动作引用与可选执行身份；不存命令原文。
- 服务端动作表在脚本解析期编译，键为脚本 id + 动作引用；命令原文、动作类型、来源路径只存在于服务端内存。
- `PlaybackGrant` 存实例 id、目标玩家 UUID 集合、创建时间与失效条件；与播放账本同生命周期，不写入脚本。
- 动作引用的具体形式由 `rule-collection.md` 的结构评审确定：目标模型使用稳定绑定/动作身份，v1 过渡可以使用脚本版本内的稳定路径；建议语义是目标模型 `bindingId + actionIndex`、v1 过渡 `clipIndex + ruleIndex + actionIndex`，字段名由结构评审定。无论哪种形式，都必须满足“服务端可唯一解析、客户端不能借它引入命令文本”。
- 动作引用不是授权凭证，只是定位；知道或猜中一个动作引用，不等于获得执行权限。授权仍由 grant 与播放账本决定，命令仍只来自服务端脚本定义。
- 审计记录存玩家、脚本、实例、动作引用、结果与时间；不存完整命令原文，避免日志二次泄露。

### 4.4 边界

- 客户端规则条件与触发时机不是安全边界。恶意客户端可以提前或重复触发一个已定义的 `emit_command`；服务端只保证命令来自脚本定义，不保证规则条件真的成立。
- 因此，只有“任何观看者在任何时刻触发都安全”的命令才适合放进 `emit_command`。需要条件门控的危险命令应放在服务端触发器/EVENT，或由服务端再次判定。
- 脚本作者仍对命令内容负责；服务端权限上限只降低误用/滥用后果，不是命令沙箱。
- EVENT 轨、MOD_EVENT、事件身份与去重不在本文范围内；它们继续按 `track-event.md` 的既有契约。
- 编辑器本地服务、预览连接与 Origin/token 防护不在本文范围内；它们不创建服务端播放授权。
- 本文不实现通用反作弊；客户端仍然可以在自己的规则求值里撒谎，服务端只收紧命令请求的“能引用什么”和“以什么权限执行”。

## 五、为什么不选别的

| 备选方案 | 做法 | 代价 | 为什么没选 |
|---|---|---|---|
| 保留原文命令，只修观看者检查 | 继续让客户端发命令字符串，只把 viewer 登记改成服务端签发 | 客户端仍可提交任意命令；必须做文本白名单/解析，容易漏 | 请求面仍然包含命令文本，根因未除 |
| 原文命令 + 脚本命令精确匹配 | 服务端收集脚本内所有 `emit_command` 字符串，要求请求文本精确匹配其中一条 | 仍暴露命令文本；`&&`、别名、空白归一化容易出错；可触发脚本内任意命令 | 动作引用比文本匹配更直接、更可审计 |
| 规则命令一律权限 0 | 用最低权限源执行 | 很多正常命令（`/give`、`/tp`、`/effect`）不可用 | 默认 2 更符合实际，危险命令仍被挡 |
| 服务端重新判定规则条件 | 把客户端规则搬到服务端执行 | 条件依赖相机/朝向/FOV 等客户端状态；仍需信任客户端；改动面过大 | 不在本轮范围；本文只收紧命令来源 |
| 删除 `emit_command` | 规则不再支持命令 | 丢失作者需要的规则动作；只能用 EVENT/触发器替代 | 保留能力，改为服务端解析动作 |
| 客户端只发动作引用，服务端解析 + 授权 + 权限上限 | 本文方案 | 需要协议/账本/动作表改动；客户端仍可提前触发已定义动作 | 能消除任意命令注入与自证观看者，边界清晰 |

**本方案的缺点**：

- 服务端不验证规则条件，客户端仍可提前或重复触发脚本里已定义的 `emit_command`；安全责任落在“作者不要把危险命令放进规则动作”上。
- 默认权限 2 会改变现有脚本行为：原先依赖规则执行 op 命令的脚本需要改用 EVENT/触发器，或由服务器运营者提高上限。
- 需要新增 grant、动作表、审计与频率限制，服务端状态和协议字段增加。
- 动作引用的序列化依赖规则集合结构评审；v1 过渡路径与目标稳定身份之间需要一次迁移。
- 频率限制只能降低滥用速度，不能阻止一次恶意触发；它不是根因修复的替代。

## 六、实现结果

状态：未实现

现行实现仍是“客户端原文命令 + 观看者检查 + 权限 4”，且观看者可由客户端播放回执登记；本文目标尚未落地。
