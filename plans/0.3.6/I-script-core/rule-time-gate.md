# 时间门与条件树：片段局部时间上的判定资格

> 状态：未实现
> 范围：共同时间基准、时间门（`>=` 阈值）、门前采集与门后提交、条件树边界、判定阶段划分
> 关联：`rule-system.md`、`rule-collection.md`、`rule-suspension.md`、`rule-facts-scheduling.md`、`rule-implementation.md`、`runtime-evaluation.md`、`loop-execution.md`、`object-model.md`

## 一、摘要

规则与曲线共用一条时间基准：**目标片段的起点是局部原点，该片段本次执行的 `[0, duration]` 是时间轴**。关键帧时间、关键帧查找与采样、规则时间门、曲线段进度都用同一个 `executionLocalTime`，不另造时钟。

时间门是绑定上的必选条件：当前局部位置 `>=` 指定时间后，门满足并开始／继续判定其它条件；不要求恰好落在该秒，也不要求观测到跨越事件。有效判定 = 外层时间门 AND 内层条件树；内层 `any` 不得绕过时间门。

## 二、时间基准

- 时间原点 = 目标片段起点；时间轴 = 该片段本次执行的 `[0, duration]`。片段在脚本时间轴上的位置 = 片段起点 + 本次执行 + 局部时间。
- 关键帧 `time` 相对片段起点；关键帧查找（游标 / 二分）与属性采样、时间门与时间类条件、曲线段进度，全部以同一个 `executionLocalTime` 为准。
- 有限片段在 `duration` 处封顶；无限片段没有自然完成点，局部时间只保证非负，不用数值哨兵冒充末端。
- 每次执行从局部 0 重新开始（反向播放从 `duration` 开始）；执行身份独立，不因时间回退或 seek 复用。时间门与曲线进度都按本次执行重新计算。
- 实时计时（超时、外部延迟）与内容局部位置分开记账；挂起期间内容局部位置不推进，实时计时不因此冻结（见 `rule-suspension.md`）。

## 三、时间门

- 每条绑定声明一个时间门：目标片段引用 + 局部时间点。时间点可由作者直接给出，或由编辑器从已有对象关键帧选取；进入判定的是确定的时间值，不是“关键帧对象必须存在”的依赖。
- 时间门在目标片段的某次执行内判定：局部位置 `>=` 指定时间后门满足，并开始／继续判定其它条件；之后成立也能执行。片段尚未开始时不满足；有限片段执行结束后局部时间固定在终止值，不再增长。
- 每次执行独立判定。循环的每次执行重新从局部 0 开始，门在新执行中重新成立；旧执行的运行态不因新执行出现而重置。
- 时间点必须落在有效局部轴内：有限 `duration` 时 `0 <= t <= duration`；无限单次片段接受非负时间点；越界在 validate 阶段报错。从关键帧选取只取该时间值，不把其它对象的关键帧并入目标片段的编号。
- 多入口用多绑定表达：不得把多个“时间 >= t”OR 成最早入口，也不得让一个绑定的成立遮蔽其它绑定（见 `rule-collection.md` §3.3）。
- 时间参照片段与动作目标片段可以不同：例如以 A 片段的局部时间或规则成功事实启动 B。不得要求尚未进入的 B 先推进自身时间才能满足启动 B 的条件；跨片段引用按显式目标与执行上下文解析。

## 四、门前采集与门后提交

- 时间门控制执行资格，不是条件监听的起点。绑定在目标执行开始后即可按各条件自身语义采集状态与事件事实；动作提交必须等门满足并完成判定。提前采集是运行态实现，不是规则生效的额外前提。
- 状态谓词与事件事实分开：状态条件按自身实时语义判定，不能把任意一度为真的状态永久锁存；事件事实按原条件的有效期、匹配与消费语义保留到门。记录起点、有效期或消费方式若原条件未定义，列为结构评审项，不假设所有历史事件永久有效。
- 提前采集按绑定与执行上下文独立；不建立无界历史记录或跨实例事件总线。
- seek：定位策略须定义提前事实在 seek 后的保留、失效或重建；seek 落到门之后必须获得有效判定，不得以缺少跨越事件为由拒绝。

## 五、条件树

- 有效判定 = 外层时间门 AND 内层条件树。
- 内层树复用底层判定能力，不复用触发器类型定义：位置／区域、结构／群系／维度、朝向／注视、实体、背包、经验、世界事件、相机状态、玩家输入，以及本实例的规则／片段事实；组合器 `all_of`／`any` 可嵌套。条件以规则自己的字段表达，不写触发器 `type`。
- 内层 `any` 只在内层成立；它不能替代或绕过外层时间门。禁止把时间条件放进内层 `any` 当作另一条入口；多时间点用多绑定表达。
- 条件看实时世界与本实例事实；判定在播放端逐实例进行；多人广播时各实例看本地玩家与相机。
- 组合优先：无语义冲突的条件、动作与出口可以组合；发生冲突时限定到具体绑定、通道或持有来源，不扩大为整组互斥。

## 六、判定阶段

规则执行中属于“判定”的部分，阶段事实不得混称：

1. **门前采集**：时间门满足前，按条件自身语义采集有效事件事实；不提前提交规则后续动作。
2. **进入控制**：时间门满足后，按声明立即建立实例级等待持有（见 `rule-suspension.md`），或保持非阻塞观察。
3. **判定**：时间门与内层条件树共同满足。时间门默认达到阈值后持续可判定，不是仅跨点当帧。
4. **判定成功**：记录本次绑定／执行的成功事实（见 `rule-facts-scheduling.md`），供后续规则或片段引用；成功事实与动作执行完成是不同状态。

规则定义只读；计时、成功、待执行与持有状态归实例、绑定与执行，不共享定义状态。

## 七、边界

- 本篇不定义挂起如何记账、动作何时提交、事实如何接力、分支去向如何决定。
- 时间门不是完成判据；完成由实际执行事实给出（见 `rule-exits.md`）。
- 判定端在播放端，逐实例；触发器仍在服务端，两者只共享底层判定核。

## 八、实现结果

状态：未实现。v1 没有时间门：规则在片段活跃窗起点激活，窗口外不判定；时间条件只能是片段本地时钟比较，门前采集与门后提交不分层。差距见 `rule-implementation.md`。
