## 1. 定位（已确认）

**这是新功能需求**（不是 bug 修复、不是使用反馈）。

两个需求：

1. **多重条件触发**：一个触发器可以要求**多个条件同时满足**（AND 组合）才触发——例如“到某个位置 **且** 看向某处”；现在的格式一个触发器只有一类条件，做不到。
2. **朝向范围条件**：检查玩家视线方向是否落在 `(yaw1, pitch1) → (yaw2, pitch2)` 范围内。按**玩家原版视线参数**判定：`yaw ∈ [-180, 180]`（0 = 南，正 = 顺时针）、`pitch ∈ [-90, 90]`（正 = 向下）；不掺模组相机侧的基准语义（`yaw_base` 等）。

**节奏**：先出本计划 → 先做**最小版本** → 看效果再扩展。

**最小版本（方向）**：JSON 手写可用 + 服务端生效 + 校验通过；只做 AND 组合、只做玩家；编辑器 UI（游戏内 + WebUI）后置。

**不是**：不是通用逻辑表达式系统（any_of / 嵌套 / 取反暂不做，但结构上不堵死）。

## 2. 现状与缺口

| 现状 | 说明 |
|---|---|
| 单个触发器 = 单一条件类型 | 23 种触发器各有一套条件字段；同一触发器内部的多字段是 AND（如 entity_kill 的场景条件），但**跨类型组合没有** |
| 同一脚本多个触发器 = **OR** | 任意一个满足就触发该脚本；没有“都满足才触发” |
| `requires` = AND，但只支持脚本状态类前置 | 内置 `script_played` / `script_started` / `script_completed`；不能把两个触发器的条件 AND 起来 |
| 无朝向检查 | 触发器里没有任何 yaw / pitch 判定；最接近的是 `observation`（看向某个**具体目标**、带 reach），做不到“朝向某角度范围” |

**缺口**：① 条件之间没有 AND 组合；② 没有纯角度的朝向判定。

---

## 3. 方案方向

### 3.1 组合层：多重条件（AND）

- 引入“**条件列表**”的写法：列表内的条件**全部满足**（AND）才允许触发；
- 列表元素**复用现有条件类型**（location / observation / entity_kill / …）+ 新增“朝向”条件；
- 现有“单条件触发器”写法**保持不动**（旧脚本零迁移）；新写法是可选的；
- 结构上给后续扩展留位置（any_of、嵌套），但**最小版本只做一层 AND**。

### 3.2 朝向条件：视线角度范围

- 条件参数 = 两对角：`(yaw1, pitch1)` 与 `(yaw2, pitch2)`；
- 判定对象 = **玩家视线**（原版参数），不需要目标、不需要射线命中——与 `observation`（看向具体目标）互补；
- 可以单独作为触发器使用（只判朝向），也可以放进条件列表与其他条件组合。

### 3.3 实现落点（方向）

- 复用现有触发器引擎：类型注册、求值器、轮询、触发状态机（`on_enter` / `exit_buffer` / `repeatable`）都不新造；
- 组合条件 = 一个“按 AND 依次求值”的条件求值器；朝向条件 = 一个新的求值器；
- 轮询频率沿用现有机制（朝向判定很便宜，是否单独设更快间隔见 §4）。

## 4. 边界与细节（要定清楚的）

1. **yaw 环绕**：区间可能跨 ±180°（例如“170° → -170°”表示穿过正北）。候选写法：① 允许端点跨越 ±180，规定“从起点顺时针到终点”；② 允许写越界值（170 → 190）再归一化。执行时二选一。
2. **边界包含性**：端点是否包含；pitch 是否钳制到 ±90。
3. **与 `on_enter` / `exit_buffer` 的关系**：组合条件下的“进入触发一次”同样依赖触发状态机——当前状态机有已知问题（见 05），最小版本可先用 `repeatable` 语义跑通，或把 05 修复列为前置。
4. **轮询频率**：朝向判定成本低；是否给朝向 / 组合触发器单独的轮询间隔（沿用现有全局配置，还是单列）。
5. **求值顺序与短路**：列表内先算便宜的条件（朝向、位置），后算贵的（射线、实体查询）；任一不满足立即短路。
6. **与 `observation` 的分工**：`observation` = “看向某个具体目标（实体 / 方块，带距离）”；朝向条件 = “视线落在某角度范围”；两者都保留，互不替代。
7. **校验与报错**：新写法的结构校验（条件列表非空、朝向端点合法、未知条件类型报错）；旧脚本零回归。
8. **编辑器与文档**：游戏内编辑器 + WebUI 的触发器编辑（组合条件增删、朝向范围编辑）后置；`TRIGGER_TYPES.md` / `SCRIPT_FORMAT.md` 随最小版本同步。

---

## 5. 用例（预期）

- **到位置 + 看向某处 → 触发脚本**（需求方给的例子）：条件列表 = [位置条件, 朝向条件]；只有同时满足才触发。
- **“不要回头”类**：玩家走到某段走廊 **且** 视线落向某角度范围（回头方向）→ 触发。
- **纯朝向触发**：只要视线进入某角度范围就触发（不带位置条件）。

## 6. 已确认 / 待定

**已确认**

- 两个需求（多重条件、朝向范围）都做：先出计划、再做最小版本。
- 朝向范围按**玩家原版视线参数**（yaw ±180、pitch ±90）。
- 最小版本：只做 AND、只做玩家、JSON 手写 + 服务端生效 + 校验通过；编辑器后置。
- 现有触发器格式不动，旧脚本零迁移。

**待定**

- yaw 环绕的区间写法（两种候选，见 §4.1）。
- 条件列表的字段形态与后续扩展方式（any_of / 嵌套；执行时定）。
- 朝向 / 组合触发器的轮询间隔（沿用还是单列）。
- 组合条件与 `on_enter` 的依赖处理（先用 repeatable，还是先修 05）。
- 编辑器支持的排期。

## 7. 验收标准（草案）

- [ ] 条件列表：全部条件满足才触发；任一不满足不触发（含轮询下的连续判定）
- [ ] 朝向范围：区间判定正确（含跨 ±180° 区间、端点边界、pitch 上下限）
- [ ] 朝向条件可单独使用，也可与位置等条件组合
- [ ] 旧格式脚本行为无变化（零回归）
- [ ] `/icinematics validate` 能校验新写法并给出可读报错
- [ ] 最小版本全程 JSON 手写可用（不依赖编辑器）

**实现约定（最小版本）**

- 条件字段：`facing` = `yaw1 / pitch1 / yaw2 / pitch2`；`all_of` = `list`（数组，元素 = `{ type, conditions }`）；
- yaw 区间语义：**从 yaw1 顺时针扫到 yaw2**（跨越 ±180° 自然环绕；起止相同 = 整圈 / 不限制）；pitch 区间取 min / max；
- `all_of` 子条件**只允许轮询类**触发器类型（location / facing / observation / structure / biome / xp / inventory / gamestage / dimension）——事件类（advancement / entity_kill / item_* 等）会带来"很久以前发生过也算"的误判，最小版本拒绝；不允许 `all_of` 嵌套。

**验收**：validate 通过；facing 可单独用；all_of 只在全真时触发（"先 A 后 B"不误判）；旧脚本零回归。**依赖**：on_enter 语义依赖 05 修复（最小版本先用 repeatable 跑通）。
