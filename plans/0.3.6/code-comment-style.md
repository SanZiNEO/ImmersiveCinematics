# 代码注释规范（0.3.6 定稿）

> 生成：2026-10-09（用户口径四条，见 §〇）。
> 适用：本仓全部 Java 源码（`common` / `fabric` / `forge`）——**对后续所有编码任务即时生效**（新写的注释直接按本规范）；存量注释按 §六「注释收敛」批次执行。编辑器（`editor/`，TypeScript）参照执行，差异见 §七。
> 依据：① 用户口径四条（2026-10-09，最高优先级，本文件主轴）；② 行业最佳实践（Javadoc 官方规范 / Google Java Style / Oracle 编码规范——**降级为补充条款**，与本项目口径的差异在 §1.3 明说）；③ 实测基线（§五，2026-10-09 统计，口径见 §5.1）；④ `plans/0.3.6/re/` 本地评估稿（不入库）；⑤ 引擎注释实践（Godot《Code style guidelines》Comment style guide、Unreal《Epic C++ Coding Standard》Comments 节，2026-10-10 调研——收敛为 §八增量条款，与 §1.3 行业口径一致处不复读）。
> 定位：本文件 = **注释写什么的规范 + 存量注释的收敛执行方案**。「为什么这么定」写在本文件里（plans 层）；**代码注释本身不写 why**。

## 〇、主轴：三层分工（用户口径，最高优先级）

**用户口径（2026-10-09，原文四条）**：

1. 注释的正文 = **公正的定义性说明**：「这个符号定义了什么、要生效什么效果、缺省 / 边界」——不写「我用了什么东西、我为什么这么写」的个人叙事。
2. 「为什么」类内容**归计划文档**（plans/，带日期 / 引用 / 裁决），不归代码注释——项目已三层分工：**plans = why、代码 = 定义 / 生效、CHANGELOG = 玩家口径**。
3. 稳定后注释必须**简化**，绝不能跟代码一样长度（当前项目 2 万行代码约 1 万行注释，属开发期临时状态，后续必须收敛）。
4. **先用命名 / 结构让代码自明**，代码说不清才补注释。

### 0.1 三层分工表

| 层 | 位置 | 写什么 | 不写什么 |
|---|---|---|---|
| **为什么** | `plans/`（带日期 / 引用 / 裁决；下一版本三篇在 `plans/0.4.0/`，只做归属标注） | 设计决策、取舍理由、调查过程、裁决记录、历史沿革、批次与进度 | — |
| **定义 / 生效** | 代码注释（本规范） | 该符号定义了什么、要生效什么效果、缺省 / 范围 / 边界 / 不变量 / 失败语义 | 「我用了什么」「我为什么这么写」、裁决出处、日期、commit、进度、计划状态 |
| **玩家口径** | `CHANGELOG.md` | 玩家可感知的新增 / 优化 / 修复 | 内部重构、代码整理、开发计划（文件头自述） |

### 0.2 四条口径在本文件的落点

| 口径 | 落点 |
|---|---|
| ① 定义性说明（写什么） | §1.1 允许清单 + §1.2 禁止清单 + §1.4 正反例 |
| ② Why 归 plans | §0.1 三层表 + §1.3 差异明说 + §6.7 搬运规则（**先搬后删**） |
| ③ 稳定后必须简化（量化） | §二 量化目标 + §五 实测基线 + §六 收敛批次 |
| ④ 命名 / 结构优先 | §2.8 提交前自检三问（删注释后是否仍自明） |

### 0.3 唯一例外（代码里允许出现的「非定义」内容）

**反直觉决策 / 复杂算法的简短指向**：允许**一行以内**，且必须链到 plans 段落（例：`背景与失败链：plans/0.3.6/multi-instance-black-screen.md §五。`）。
不允许：把 plans 的内容抄进代码、复述调查过程、写裁决日期与人物。

## 一、注释写什么 / 不写什么

### 1.1 写（定义 / 生效 / 缺省 / 边界）

按优先级：

1. **契约**：该符号对使用者的承诺——输入输出含义、不变量、失败语义（例：`applyTo` 返回 `false` = 本层未施加；lane 合成失败 = 整个跳过这次绘制）。
2. **缺省与范围**：字段缺省值、取值区间、单位、越界处置（例：`-1 ~ 1`、缺省 `0` = 无效果、`0 ~ 1` 缺省 `1`）。
3. **边界与特例**：什么条件下不做 / 跳过 / 回落（例：十二通道全 0 = 整步跳过、逐位恒等；无曲线时强度被忽略）。
4. **公式与顺序**：只有一处定义点需要完整写出（见 §2.4），其余位置只写「第 n 步」或链接。
5. **外部平台事实**：构成定义前提的平台约束（例：MC 1.20.1 `GlStateManager` 12 个纹理单元上限、`ShaderInstance` 的采样器压缩口径）——这类可以留，因为它是定义的一部分。
6. **维护不变式**：改一处必须同步另一处的地方（例：`LutBindGuard.DECLARED_SAMPLERS` 增删采样器必须与 `ic_color_adjust.json` 同步）。

### 1.2 不写（禁止清单）

| 类型 | 例（真实） | 处置 |
|---|---|---|
| **个人叙事 / why / 裁决出处** | `ColorAdjustPass` 失败语义节里的「（用户裁决 2026-10-09，见 …）」与调查故事 | 搬 plans 后删（§6.7） |
| **复述代码** | 逐字段复读：`TrackSchemas` 六色带 12 行 `// -1 ~ 1（X带色相旋转）`（块注释已说清） | 删；块注释定义一次 |
| **历史 / 沿革** | 「0.3.6 新增」「原实现为 …」「此前在 `LaneRendererMixin` 里」 | 搬 plans / CHANGELOG 后删 |
| **进度 / 计划状态** | 「已落地」「尚未实现」「下一步」「🔵」 | 删（进度归 `implementation-progress.md`） |
| **日期 / commit / 批次号** | 「2026-10-08 后移」「`6deb2d7`」「A13'」 | 删（TODO 标记除外，见 §三） |
| **HTML 排版标签** | `<h2>` / `<p>` / `<b>` / `<ol>` / `<li>` / `<table>` | 转纯文本 + 空行分段（§2.6） |
| **多行复读** | 同一机制 10 处完整描述（六色带：Java 6 + 着色器 6）、10 处复述（alpha 直通契约） | 收敛为 1~2 处定义点 + ≤1 行指向（§2.4） |

**注意区分**：`{@code}` / `{@link}` / `{@literal}` 是 **javadoc 内联标签**（保留），不是 HTML 排版标签；`&lt;` / `&gt;` / `&amp;` 三个转义实体保留（含 `<` `>` 的内容优先用 `{@code}` 承载）。

### 1.3 与行业素材的差异（明说）

| 议题 | 行业主张（Javadoc / Google / Oracle） | 本项目口径 | 落地方式 |
|---|---|---|---|
| 「为什么」写哪 | 注释解释 **Why**（代码写 How） | **Why 归 plans**（带日期 / 引用 / 裁决） | 代码注释只写定义 / 生效；反直觉决策留 ≤1 行指向 plans（§0.3） |
| 注释密度 | 好注释不嫌多；「注释与代码同长也可接受」 | **上限硬约束 ≤25%**（§2.1），稳定后必须简化 | 定义点唯一化 + 删复读（§2.4） |
| 自解释性 | 注释补充代码表达不了的意图 | **命名 / 结构优先**，注释是最后手段 | 提交前自检三问（§2.8） |
| 文件头 | 版权 / 作者 / 变更历史头 | **不写文件头**（现状一致：本仓无文件头） | 类 javadoc 直接挂在 `class` 上 |
| 标记 | TODO / FIXME 自由使用 | **必须带任务 ID 或 plans 链接**（§三） | 无主标记不许新增 |
| HTML | 允许（javadoc 支持 HTML） | **禁排版标签**（§2.6） | 空行分段 + `{@code}` / `{@link}` |

保留的行业条款（与本项目口径不冲突）：① javadoc 标签顺序 `@param` → `@return` → `@throws`（§2.3）；② 同步更新——**过时注释比没有注释更糟**（§2.7）；③ 不用注释代替糟糕的代码（先改名 / 拆方法，再补注释）。

## 二、量化目标

> 25% 是**上限不是配额**：为了凑数字删掉定义性内容 = 违规；只删 why / 复读 / 过时。

### 2.1 注释总量（硬目标）

| 指标 | 目标 | 基线（2026-10-09） |
|---|---|---|
| 全仓注释行 / 代码行 | **≤ 25%** | **33%**（6,844 / 20,569） |
| 单文件注释行 / 代码行 | **≤ 50%**（软目标） | 13 个文件注释行 ≥ 代码行（注释 ≥ 30 行） |

- 豁免：接口 / 枚举 / record 等**纯声明文件**（代码行 < 100），其 javadoc 即内容；但**每个成员的 javadoc ≤ 3 行**。
- 达标账：需删约 **1,700 行**注释（6,844 → ≤ 5,142）；由 §六 分片 S1–S4 承担，S5 / S6 已达标（只做合规清扫）。

### 2.2 类 javadoc

- 正文 **≤ 15 行**（空行、标签行不计；含小节标题行）。
- 只写：职责一句话 + 契约 / 缺省 / 边界 + 定义点公式（若该类是定义点）。
- 超过 15 行 = 信号：内容该进 plans，或该类该拆（如 `CameraManager` → B4 `camera-core-split.md`）。

### 2.3 方法 javadoc

- 正文 **≤ 5 行**；标签每项 **≤ 1 行**。
- 标签顺序固定：`@param` → `@return` → `@throws`（行业补充条款，保留）。
- 写 / 不写：
  - 写：公共 / 受保护成员的**契约不显然者**（边界、缺省、失败语义、参数含义、副作用）；
  - 不写：命名已自明的 getter / setter / 简单转发 / 私有辅助方法（复杂逻辑改用行内注释，只解释「这里在做什么定义」）。
- 参数含义在正文一句能说清时，**省略 `@param`**（不写 `@param name 名字` 这类零信息标签）。

### 2.4 单概念单处完整定义（禁三处复读）

- 同一机制（同一信息面）的完整描述（≥ 2 行）全仓只允许 **1 处**——即**定义点**；其余出现只允许 **≤ 1 行指向**（`{@link}` 或 `见 …`）。一个机制允许有**两个不相交的定义点**（如「公式」在实现处、「参数语义」在参数类），但**同一信息不得有两处**（见 §1.4 例 C）。
- **禁三处复读**：任何概念出现 ≥ 3 处多行复述 = 违规（基线违规例：六色带 10 处、alpha 直通契约 10 处）。
- 定义点选择规则（离被定义物最近的一处）：

| 概念类型 | 定义点 |
|---|---|
| 字段语义 / 范围 / 缺省 | schema 字段表（`script/schema/TrackSchemas`） |
| 参数快照语义 / 公式 / 操作栈顺序 | 参数类（如 `client/post/ColorAdjustParams`） |
| 着色器契约 / 像素级公式（alpha 直通、操作栈步骤号、六色带权重等） | `ic_color_adjust.fsh` 对应**实现处**（公式）+ 文件头（步骤清单 / 契约）；Java 侧只写参数语义 + 一行指向 |
| 失败 / 守门语义（fail-safe） | 契约执行者（`ColorAdjustPass` / `LaneComposeGate` / `LaneRenderer.renderLane`） |
| 平台约束（采样器单元压缩等） | 该约束的复刻类（`LutBindGuard`） |

- 收敛批次开工前先产出「**定义点登记表**」（§6.2），逐概念登记「定义点 + 允许的指向处」。

### 2.5 行宽

- **注释行 ≤ 100 列**（基线 6,670 行中仅 37 行超宽，0.6%）。
- 新增代码行 ≤ 120 列；存量超宽代码行不在注释收敛范围（纯注释 diff 原则，§6.5）。

### 2.6 禁 HTML 排版标签

- 禁：`<h1>`~`<h6>` / `<p>` / `<b>` / `<i>` / `<u>` / `<ul>` / `<ol>` / `<li>` / `<table>` / `<tr>` / `<td>` / `<br>` / `<blockquote>`。
- 替代：空行分段；小标题用一行纯文本（如 `挂点：…`）；强调用「」或直接不强调；含 `<` `>` 的内容用 `{@code}` 承载。
- 保留：`{@code}` / `{@link}` / `{@linkplain}` / `{@literal}` / `{@inheritDoc}` 与 `&lt;` / `&gt;` / `&amp;`。

### 2.7 同步更新

- **改行为必须在同一 commit 改对应注释**；注释与代码矛盾时以代码为准，并把矛盾登记（可能是文档滞后 bug）。
- 删除行为 / 字段时，其注释一并删除（版本原则：不留旧路径、不写「原实现」）。

### 2.8 命名 / 结构优先（提交前自检三问）

1. **删掉测试**：删掉这条注释，读者能否从命名 / 结构 / 既有定义点得到同样信息？能 → 不写。
2. **对象测试**：这条注释描述的对象是「代码符号」还是「人 / 过程 / 历史」？后者 → 不写（归 plans）。
3. **时间测试**：这条注释 6 个月后是否仍然成立（不含「本次 / 现在 / 此前 / 尚未」）？否 → 改写为现状定义或删。

### 6.5 纯注释 diff 判定（机械 + 硬证明）

```sh
# ① 机械检查：diff 中不允许出现「非注释、非空行」的增删（期望：无输出）
git diff -U0 -- '*.java' | awk '/^[+-]/ && !/^(\+\+\+|---)/' \
  | awk '!/^[+-][[:space:]]*(\/\/|\/\*|\*|\*\/)/ && !/^[+-][[:space:]]*$/'

# ② 硬证明：剥离注释与空行后，前后源码逐字节一致
#    剥离器（一次性脚本，放 .planning/036-impl/comment-strip.sh）：去掉行首注释行、行尾 // 片段、空行；
#    对每个改动文件比对 `git show HEAD:<file>` 与工作区版本，期望逐字节一致。
```

- ① 漏掉「行尾注释删除」（该行是代码行）→ 行尾注释场景一律以 ② 的逐字节比对为准，并人工复核该行。
- ② 通过 = 逻辑零动的**硬证明**；三套冒烟（§6.6）是兜底，不替代 ②。

## 八、引擎注释增量（2026-10-10，批次 B 起编码任务书必带）

> 调研素材：① Godot《Code style guidelines》Comment style guide——不要复述代码、解释定义而非过程、成员变量用单行注释（不用 javadoc）、注释约 100 列换行、`TODO/FIXME/NOTE/HACK` 作告示语；② Unreal《Epic C++ Coding Standard》Comments 节（引 Kernighan & Pike《The Practice of Programming》）——自文档化命名优先、写有用的注释、烂代码不许用注释补（改写代码）、注释不得与代码矛盾。两者与 §一~§四一致处不复读；本节只补**引擎域（相机 / 渲染 / 剔除 / 数学模型）特有的注释义务**。

### 8.1 引擎域必写定义清单（定义点涉及即必写，每项一行量级）

1. **单位**：角度（度 / 弧度 / 归一化）、时间（秒 / ms / tick）、长度（方块 / 像素 / 归一化 0~1）——字段与参数语义带单位词。
2. **坐标空间与轴向**：世界 / 相机 / 屏幕 / 素材空间；yaw-pitch-roll 施加顺序与正方向；原点基准（玩家眼睛 / 相机位置 / 素材左上角）。
3. **数值契约**：取值区间与越界处置（clip / wrap / 拒绝 + 回落）、容差与退化输入（零长度 / 纯垂直线 / NaN / dt=0）的行为、精度口径（何处取整、何处保持浮点）。
4. **不变量**：任何时刻必须成立的关系（如 alpha 逐位直通、统一快照唯一读侧出口），写在**保证它的符号**上。
5. **分配 / 线程 / 频率契约**：零分配路径标注（通用原则「零分配」条）、仅客户端线程 / 仅渲染线程、调用频率（每帧 / 每 tick / 一次性）。
6. **状态所有权**：GL 状态 / 注册表 / 缓存的创建者、释放者、生命周期挂点。
7. **平台事实**：构成定义前提的 MC / Forge / GL 约束（§1.1 第 5 条同口径）。

### 8.2 负面清单增量

- 公式推导过程 / 示意图式注释 → 只留公式一行 + 指向 plans 或引用出处（§0.3 同口径）。
- 「与 Unreal / ReplayMod 一致」这类出处叙事 → 归 plans；代码只写本仓语义定义。
- 成员字段整段 javadoc → 单行注释（Godot 口径）；字段语义复杂的写进类 javadoc 定义节，字段行不复读。
- 注释与代码矛盾 = 违规（Unreal 口径，同 §2.7）：以代码为准并登记。

### 8.3 任务书注释口径（编码任务书「口径」行固定携带）

> 注释按 `plans/0.3.6/code-comment-style.md` §一~§四 + §8.1：定义 / 生效 / 缺省 / 边界写足（单位、坐标空间、数值契约、不变量、分配/线程契约不许缺），why 与出处归 plans；类 javadoc ≤15 行、方法 ≤5 行、标签顺序 `@param`→`@return`→`@throws`；禁 HTML 排版标签、禁无主标记、禁复读（同概念 ≤1 处完整定义）；改行为同 commit 改注释；提交前过「附：提交前自检清单」。
