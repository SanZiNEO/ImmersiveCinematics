## 1. 定位（已确认）

**模板 = 参数化生成器**：用户填目标需求（"围绕 X 转一圈看向它"），模板内部展开成标准脚本 JSON——用户不需要懂曲线 / 关键帧 / 轨道的具体写法。

**现状（0.3.5 的预设系统已随编辑器退役删除）**：

| 现状 | 说明 |
|---|---|
| 代码 | ~~`editor/preset/`：`Preset`（接口）、`PresetParam`（参数声明 record）、`PresetRegistry`（注册表）、`OrbitCirclePreset`（环绕轨道）~~ ——**已删除**（0.3.6 游戏内编辑器退役，见[编辑器 WebUI 迁移](./editor-webui-migration.md) §4）；模板体系**从零新建** |
| 内置库 | 0 个（原唯一预设"环绕轨道"随之删除：三段三阶贝塞尔拼圆，控制点距离 = `R × 4/3 × tan(θ/4)` ≈ 0.7698R——算法留档在 `plans/complete/0.3.5/presets.md` 与 git 历史） |
| 形态 | 原形态：**扁平、一次性**（生成函数直接产出整份脚本 / 整个 clip，参数 schema 与 `script/schema` 的 `FieldDef` 是两套）；新体系按 §2 三层模型重建 |
| 原则（0.3.5 已定，沿用） | 生成结果 = 标准脚本 JSON，走 `ScriptParser` / `ScriptValidator` 校验，与手写脚本完全等价、可继续编辑（不是黑盒）；初版只做内置模板（生成逻辑在 Java 代码，非纯数据） |

**目标（已确认·2026-10-07）**：从"一个贝塞尔预设"发展为**脚本-轨道-片段 三层模板体系**——复杂效果 = 分层模板的组合，用户只需要填几个目标参数。

### 落地记录（2026-10-07 · 第一版 = 步骤 1-2）

代码：`common/src/main/java/.../script/template/`。

- **参数声明与 schema 合并（步骤 1）**：模板参数 = `TemplateParam`（key + 显示名 + **复用 `script/schema` 的 `FieldDef`**），不是第二套 `PresetParam`——类型 / 默认值 / 枚举候选 / `section` 分组全部走 FieldDef，将来直接吃 `schema.get` 驱动的表单。
- **展开器（步骤 1）**：`ClipTemplate.expand(TemplateArgs) → clip JSON`（Java 函数）；`TemplateArgs` 按声明归一实参并兜默认值（展开器不用自己判空）；`TemplateRegistry` = 注册表（当前即内置库，id 空间为片段级）。
- **嵌套引用**：本版**未实现**——片段级是三层的最底层，没有可引用的下层；`id` 引用留给步骤 3（轨道级引用片段级）落地时定（倾向：轨道模板按 id 引用片段模板并逐层传参）。
- **产物与校验**：`TemplateScriptAssembler` 把展开出的 clip 装进 `ScriptTemplate` 骨架 → 标准脚本 JSON，走 `ScriptValidator`。冒烟：4 个模板 × 默认 / 非默认参数共 13 组展开 → 装配 → 校验，问题数 0；环绕弧线另做几何核对（贝塞尔采样点相对圆的半径误差 < 0.2%，θ=120°）。
- **接入点**：`/icinematics template list` 与 `/icinematics template <id> [key=value ...]`——后者展开 → 写 `scripts/generated/<name>.json` → 当场 `ScriptValidator` 校验（不过则不落盘）。**选命令而非 WebUI**：纯 common 侧、与既有 `/icinematics validate` 同一条"生成→自查→播放"闭环、无需改 TS 前端。

**第一批片段模板（4 个）**：`fade`（黑场/白场，OVERLAY 轨）、`static_breath`（固定 + 呼吸）、`dolly`（推近/拉远）、`orbit_arc`（环绕弧线，单段 ≤120°）。
取舍：**希区柯克不单列模板**（= `dolly` 的两个 fov 两端不同，同一条位置路径）；**"环绕整圈"不做片段模板**（三段 120° 拼圆 = 轨道级，属步骤 3）——`orbit_arc` 只负责其中一段，超限直接拒绝并提示。

## 2. 三层模板模型（已确认方向）

```text
脚本级模板（Script Template）
  ├─ 生成整份脚本骨架：meta（含循环 / 可跳过 / 听者等默认值）+ 触发器 + requires
  ├─ 引用 轨道级模板 × N（每条轨道一个）
  └─ 可带默认转场（黑场 / 叠化 …，引用 scene-transition.md）
       ↓
轨道级模板（Track Template）
  ├─ 生成一条轨道的 clips 编排（如"环绕整圈 = 三个 120° 片段"、"A→B 双机位切轨"）
  └─ 引用 片段级模板 × N
       ↓
片段级模板（Clip Template）
  └─ 生成一段镜头（如"推近"、"环绕 90°"、"固定 + 呼吸"）——一个 CAMERA clip 的关键帧
```

| 层级 | 例子 | 生成物 |
|---|---|---|
| 片段级 | 推近 / 拉远 / 环绕 90° / 固定 + 呼吸 / 希区柯克变焦 | 一段 clip（关键帧 + 轨迹） |
| 轨道级 | 环绕整圈（三片段拼圆）、多机位切轨 | 一条轨道的 clips |
| 脚本级 | "跟随蓝方 + 看向红方 30s，转完黑场退出" | 整份脚本（meta + 轨道 + 触发器 + 转场） |

**0.3.5 的 `OrbitCirclePreset` 已随 `editor/` 包删除**（0.3.6）：它当年横跨三层（直接产出整份脚本的环绕内容），不能直接复用——新体系的落点是**片段级模板"环绕 120°"×3 组成的轨道级模板"环绕整圈"**，参数（圆心 / 半径 / 高度 / 朝向 / 圈数 / 时长）下放到对应层；环绕算法按上表留档参考重写。

## 3. 模板的模型（先定义工具，再谈调用）

与用户原则一致（先定义工具 → 再考虑调用 / 整合）：本文先定义"模板是什么"，编辑器面板 / 命令 / 插入点都是后续调用方。

**模板 = 参数声明 + 展开规则 + 可嵌套引用（方向）**：

1. **参数声明**：与 `script/schema` 同源（`FieldDef`），而不是现在的第二套 `PresetParam`——合并后模板参数天然吃 schema 驱动的表单（`editor-webui-migration.md` 的 `schema.get` 链路）。参数类型覆盖位置 / 选择器 / 数值 / 枚举等（脚本模型 §4 的"参数声明"是同一条底层线）。
2. **展开规则**：Java 注册的生成函数（输入参数对象 → 输出对应层的 JSON 片段）；数学（贝塞尔拼圆、轨迹计算）落在这一层，复用 `BezierCurve` / `MathUtil` / `BezierPathStrategy` / `ArcLengthLUT` 等底层。
3. **可嵌套引用**：脚本模板引用轨道模板、轨道模板引用片段模板（`id` 引用）；引用时逐层传参。
4. **产物**：标准脚本 JSON，走 `ScriptParser` / `ScriptValidator`——与手写等价、可编辑（沿用 0.3.5 原则）。

**模板是"调用方"，不是底层**：它调用的底层是轨迹数学、关键帧体系、schema 参数声明、坐标源 / 选择器（基准）、转场（脚本级模板默认转场）。这些底层成熟后，模板只是"组合"。**新增一个底层能力（如新曲线类型、新坐标源），模板自动受益。**

## 4. 可能的问题

- 模板参数与运行时基准（相对坐标 / 选择器 / 触发点）的关系：模板生成的脚本引用实体 / 触发点，运行时解析——与坐标源、选择器的现状差距（selector-model / coordinate-frame 的已确认方向）联动。
- 三层之间传参的形态（参数继承 / 覆盖 / 命名空间）。
- 自定义模板：初版内置（生成逻辑是代码）；"纯数据模板"需要可计算字段与表达式（math-models 的 JSON 模型化）成熟后才有意义——远期。
- 生成结果的可编辑性：沿用"生成普通脚本"（作者改完不再与模板关联，或保留模板来源标记用于再生成——待定）。
- 模板版本化：模板升级后，已生成的脚本是否受牵连（倾向：生成即脱离，模板升级只影响新生成）。
- 编辑器呈现：模板面板 = schema 表单 + 实时预览（帧推流已有）+ 插入位置（当前时间点 / 新脚本）。
