本页只做索引与决策记录，不重复各文档正文。一个点一篇文档；组件、协议、步骤以各文档为准。

## 一、定义

编辑器是**固定格式脚本的生成器**。它不是视频剪辑器，也不是构图编辑器：时间轴、预览、参数面板都为产出脚本服务，产物由模组侧解析与播放模块唯一确认。

编辑器的两个载体见 §八：WebUI 外部编辑器（Electron，跨进程）与游戏内编辑器（晴雪 UI 附属模组，同进程）；旧游戏内 Java 编辑器已退役。两者共用同一套消息与模型，不各自维护第二套语义。

- 产物是模组可解析的标准脚本；编辑器不定义格式，也不改运行时语义。
- 生成包含优化：编辑器把底层能力整合、优化成效果，细分到每一项效果都能快捷生成——作者想要环绕、黑场、划像这类效果，不必考虑底层怎么组合，编辑器按底层规则把该有的效果拼出来。
- 作者的输入是“要什么效果”，不是“底层字段怎么填”。

## 二、为什么做

### 2.1 问题

- 游戏内编辑器编译在模组里，每个 Minecraft 版本都要重新适配，一份编辑器对接不了多个版本。
- 它占模组 Java 代码三分之一左右，自带文件读写、预览捕获与整套 UI，与播放解析混在一处。
- 作者只能在游戏里改脚本，改完切回游戏看效果，一轮迭代成本接近重开游戏。

### 2.2 目标

- 一份编辑器对接所有版本：字段由模组侧 schema 描述，编辑器按 schema 渲染表单。
- 不启动游戏也能打开界面，用示例数据浏览与编辑。
- 游戏内按键后，编辑器能读写脚本、校验、看实时画面、控制播放、进飞控取景。
- 新增字段只需改 schema 并补一个控件。
- 只有本机编辑器能连上；脚本数据模型与字段元数据不随编辑器存亡。

### 2.3 非目标

- 不做视频剪辑器：媒体导入、转码、特效库都不做。
- 不做构图编辑器：时间轴与预览只为产出脚本服务。
- 不把前端打包进模组 jar，不托管成网页，不做远程访问。
- 不保留旧游戏内 Java 编辑器；游戏内编辑器由晴雪 UI 附属模组承载（§八）。

## 三、形态与能力

### 3.1 形态

独立的 Windows 小工具（Vue 3 + TypeScript + Vite + Electron），不随模组分发，已打出安装包（0.1.0，测试中）。源码在独立编辑器仓库（规划：`webui` 分支为主；主线不再包含编辑器源码，旧 `editor` 分支迁移后删除）；游戏内编辑器是同一能力的晴雪 UI 附属模组形态，按 MC/AUI 版本分支。带离线演示模式：没连游戏时也能浏览界面与示例脚本。游戏内按 F9 打开预览屏并启动本地服务，编辑器连上 `ws://127.0.0.1:8765/ws` 即可工作，关屏即断开。mod 是服务端，编辑器是客户端。

### 3.2 能力

脚本管理（新建、打开、保存、删除、校验）、meta 与轨道、片段、关键帧与触发器编辑、播放控制、实时预览、飞控取景、撤销重做、A-B 循环、marker、快捷键与中英双语。时间轴与预览是产出脚本的辅助，不是通用剪辑能力。

### 3.3 权威

权威始终在模组侧：编辑器不直接读文件、不自己解析，字段有哪些、脚本是否合法都经协议回答；加一个字段等于改 schema 加一个控件。字段元数据归 `script/schema/`，独立于任何编辑器存在。

## 五、方案取舍

| 备选方案 | 做法 | 代价 | 为什么没选 |
|---|---|---|---|
| 继续保留游戏内 Java 编辑器 | UI 留在模组内 | 每版本重适配、改字段重编译 | 一份编辑器对接所有版本更划算 |
| 以 Olive / lossless-cut 为壳 | 取用开源剪辑器代码 | 两者是 GPL（Olive GPL-3.0、lossless-cut GPL-2.0-only），本项目 MIT，会被迫改许可 | 许可不可行 |
| 以 MIT 剪辑软件为基座 | 用现成剪辑器改 | 素材是媒体、核心是切片段，与脚本生成器不同构 | 结构不采用，只借交互外形 |
| 模组托管网页给浏览器 | 服务端出页面 | 页面读不到凭据、权限受限 | 桌面客户端更合适 |
| 引第三方 WebSocket 库 | 现成库做握手与帧 | 多一份依赖与打包成本 | 需求只有文本帧、二进制帧与单机连接 |
| 引重型图库（d3 / cytoscape / G6）做架构图 | 现成布局与画布 | 依赖体积、样式难贴合分区语义 | 自研布局更可控 |
| 力导向布局 | 物理模拟 | 每次结果不同、文件夹语义丢失 | 拓扑分层可重复 |
| 只画脚本级依赖 | 同一对脚本的多条前置合成一条 | 丢失触发器粒度 | 边保留触发器与条件 |

**本方案的缺点**：预览屏不开就用不了，失去“不切窗口”的便利；服务端仍在模组内，跨版本适配只解决一半；飞控单独镜头依赖多相机画面与预览隔离，链路长；预览编码依赖外部 ffmpeg（无 ffmpeg 回退原始像素、带宽高），单凭据无权限分级；架构图大包规模下的渲染方式未定，前置成环只能提示，布局不能由作者保留，图不随脚本增删改自动更新。

从 Olive 借的是设计思路（不受版权保护）：变换按序列分辨率归一化到 [-1,1]、Fit / Fill / Stretch 适配三档、关键帧自带插值 + 贝塞尔手柄、向量按分量分轨、裁切四边 0~1 归一化。lossless-cut 用的 `electron-vite` 脚手架本身是 MIT，但编辑器已是同一套栈，fork 它是降级。

## 八、运行形态与分发（2026-11-06 讨论）

> 本节记录用户 2026-11-06 给出的口径与实现要求：运行形态、配置开关、编辑器底层接口（画面 / 信号）。

### 8.1 阶段

1. **近期**：继续用 WebUI 编辑器（现有 Electron 客户端 + 模组内 WebSocket 服务）。
2. **打磨完成后**：把编辑器做成**附属模组**（ImmersiveCinematics Editor）。晴雪 UI 是它的前置库，主模组是它的运行依赖（只做壳子没有意义）；编辑器相关代码与依赖不再占用主模组发布包。
3. **版本**：附属模组独立版本号；每次发布注明 `for <主模组版本>`。

### 8.2 配置开关（重要）

编辑器基本只有作者使用，因此模组配置文件里保留一个**编辑器开关**：

- **默认开启**（方便作者编辑）。
- **关闭时**：编辑器部分对用户**不可见、不可用**——与编辑器的通信功能、编辑器特有按键与按键绑定列表、预览入口、编辑器专用资源与服务全部不加载、不生效。
- **只作用于客户端**：编辑器是产出脚本的外部工具，不是服务端组件；服务端不加载任何编辑器薄壳。
- 这是「运行期薄壳开关」，不是已退役的 `editorEnabled`（那个管游戏内 Java 编辑器，已随 2026-10-07 退役删除）；新开关的语义是「编辑器附属能力是否启用」。

### 8.3 预留接口：画面传输 + 信号传输

主模组向编辑器（外部 WebUI 或游戏内附属模组）暴露两类底层接口。接口是纯 Java 契约，主模组不依赖晴雪 UI。

设计取三者之长：

| 来源 | 采用的优点 |
|---|---|
| 内置编辑器（已退役） | 同进程 GPU 内传递、在编辑器 UI 前捕获（预览不含编辑器界面）、UI 事件只记意图 + tick 节流派发 |
| WebUI（现状） | 协议化消息集（请求 / 回执 / 推送）、schema 权威、状态推送、跨进程能力 |
| 晴雪 UI（ApricityUI） | HTML / CSS / JS、纯 Java 渲染、体积不到 1 MB、热重载与开发者工具、Webview |

#### 8.3.1 画面传输

只负责把游戏画面送到编辑器侧；纹理管理、缩放、读回细节不暴露给编辑器。

要实现的行为：

- **内容**：**主画面（窗口 framebuffer），含 HUD、覆盖层、lane 合成与调色**，不含编辑器自己的 UI。捕获点 = 世界 + HUD 之后、编辑器 UI 之前（`hud`，见 [`../J-media/capture.md`](../J-media/capture.md) §3.1）；预览固定 1080p60。依据 [`../G-script-model/editor-playback.md`](../G-script-model/editor-playback.md) §3.2 / §八；验收记录 `capture src=main -> 1920x1080（含 HUD / lane / 调色）`。
- **时机**：沿用原版**聊天屏**的 HUD 处理方式——Screen 打开时 HUD 照常渲染，编辑器 UI 叠加在其上；每帧在 HUD 与覆盖层绘制之后、编辑器 UI 绘制之前传输，因此预览含 HUD、不含编辑器界面。
- **尺寸**：固定 1920×1080@60；窗口 / 分辨率变化不影响输出（`CaptureHub` 规格固定）。
- **传输形态按消费方选择**：
  - 同进程（游戏内编辑器 / 晴雪 UI）：GPU 内完成（blit 到编辑器可消费的目标或等价方式），不读回 CPU、不走网络。
  - 跨进程（WebUI）：固定 1080p60 帧流——有 FFmpeg 用 H.264 编码流，无 FFmpeg 用原始 RGBA。
- **生命周期**：编辑器打开时建立，关闭时释放；重复关闭幂等。
- **失败**：画面不可用（尺寸非法 / FBO 不完整）时编辑器显示占位，不影响游戏与播放。

**原版依据（MC 1.20.1 `GameRenderer.render`，2026-11-07 源码核查）**：

- HUD 渲染条件：`if (!this.minecraft.options.hideGui || this.minecraft.screen != null) { this.minecraft.gui.render(...); }`——**只要 `screen != null`，即使 `hideGui == true`，HUD 也照常渲染**；Screen 在 HUD 之后绘制。
- `ChatScreen.render` 只画输入框那一小条，**不调用 `renderBackground`**，所以聊天打开时 HUD 保留。
- `InventoryScreen.render` 第一行调用 `renderBackground`；`Screen.renderBackground` 在有世界时用 `fillGradient(0, 0, width, height, -1072689136, -804253680)` 画全屏半透明黑，把先画好的 HUD 盖掉——这是 E 键物品栏看起来「隐藏 HUD」的原因。
- 编辑器预览走**聊天屏**这条路：保持 `screen != null`、不画全屏背景，HUD 与脚本 / 白名单放行的层自然保留；**不额外加编辑器专用 HUD 限制**。

#### 8.3.2 信号传输

**直接复用 WebUI 现有的一套信号**：游戏内编辑器与 WebUI 共用同一消息语义，不另造第二套。

要实现的行为：

- 请求 / 回执 / 推送三种形态保持一致。
- 脚本：`script.list` / `load` / `save` / `delete` / `new` / `validate`。
- 元数据：`schema.get`、`registry.query`、`script.graph`、`resource.list`。
- 播放控制：`editor.seek` / `play` / `pause` / `stop` / `setCamera` / `pushScript`。
- 状态推送：`playback.state`、`flight.state`、`error`。
- 派发沿用内置编辑器的经验：UI 事件只记录意图，在 tick 里派发；时间同步节流 50 ms、脚本推送节流 200 ms。
- 游戏内编辑器与 WebUI 的差异只在传输载体（进程内调用 vs WebSocket），消息语义相同。

#### 8.3.3 边界

- **编辑器定义**：产出固定格式脚本的图形工具，与模组通信极少、无任何依赖；模组不依赖编辑器，编辑器不参与播放、渲染、服务端逻辑。
- 主模组**不需要任何 GUI**；只有附属模组使用晴雪 UI。
- 附属模组依赖「接口 + 晴雪 UI + 主模组」，不直接读主模组内部类。
- 附属模组**直接使用主模组已有能力**（脚本读写、schema、播放控制、画面传输、飞控状态），不重复实现播放 / 渲染 / 媒体链路。
- 接口放在对外稳定面（`api/` 或独立编辑器接口包），只增不删。

### 8.4 两种消费方

| 消费方 | 载体 | 画面 | 信号 |
|---|---|---|---|
| WebUI（外部 Electron） | 跨进程 WebSocket | 固定 1080p60 帧流：有 FFmpeg 用 H.264 编码流，无 FFmpeg 退回原始 RGBA | WebUI 消息集 |
| 游戏内编辑器（晴雪 UI，附属模组） | 同进程 | 8.3.1 画面传输：GPU 内完成，不读回 CPU、不走网络 | 同一套 WebUI 消息集（进程内调用） |

### 8.5 晴雪 UI 的能力与定位（2026-11-06 确认）

晴雪 UI（ApricityUI）是用 HTML / CSS / JS 构建 Minecraft UI 的框架，关键事实：

| 项 | 事实 |
|---|---|
| 实现 | 纯 Java 实现，不打包 Chromium；体积不到 1 MB |
| 语法 | 尽量遵循 Web 标准；遮罩嵌套、平滑滚动、圆角边框、毛玻璃、自定义动画、自定义字体、GIF、滤镜 / 遮罩 / 阴影互相嵌套 |
| 开发体验 | 支持热重载与开发者工具 |
| 扩展 | 可作为依赖给其他模组绘制 UI；也可渲染在世界中的方块上 |
| Webview | 1.2.5+ 支持调用操作系统内置 Webview，嵌入可播放视频的真实网页 |
| 版本 | 支持 Fabric / NeoForge / Forge 多版本；与本项目相关的 **1.20.1 Fabric / Forge** 都在支持列表内 |

**定位**：主模组**不依赖晴雪 UI**；它只是编辑器附属模组的实现基础。主模组只预留接入方法，让作者或附属模组能方便地写基于晴雪 UI 的编辑器。支持版本广是顺手可用的加分项，不是本项目的主线。

### 8.6 版本与跨版本

- 晴雪 UI 支持的游戏版本足够前期使用；附属模组不是必须的，WebUI 编辑器可以独立工作。
- 本版本先把脚本格式与内容稳定下来。
- 跨游戏版本尽量保持统一 schema；缺失的能力逐项补齐。
- 一个 WebUI 编辑器产出的脚本可以跨版本通用；Forge / Fabric 层本身很少，迁移方便，不需要为此单独验证。

### 8.7 落地顺序（要实现什么）

1. **画面传输接口**：抽出「HUD 与覆盖层绘制之后、编辑器 UI 之前」的捕获与传输；同进程路径先跑通，用现有编辑器预览做首个消费者。
2. **信号接口**：把 WebUI 的消息处理从 WebSocket 会话中解耦成独立处理器；游戏内调用直接走同一个处理器。
3. **编辑器薄壳开关**：按 8.2 的清单，关闭时按键 / 绑定 / 预览入口 / 服务端 / 协议端点 / 资源都不加载。
4. **附属模组**：基于晴雪 UI 实现游戏内编辑器，接 8.3 的画面与信号两类接口。
5. **统一行为**：WebUI 与游戏内编辑器共用同一套信号实现，避免两套逻辑漂移。

### 8.8 仓库与分支（2026-11-08）

- 编辑器源码与发布在**独立编辑器仓库**：主模组仓不再包含编辑器源码 / 前端产物。
- `webui` 分支：一个分支跨 MC 版本；schema 已稳定，少数版本差异做适配，不为每个 MC 版本开分支。
- `ingame/<mc>` 分支：按 AUI 前置支持的 MC 版本分支；共用同一套消息 / 模型，只保留加载器薄壳与 AUI 绑定差异。
- 主模组仓保留：对外 API、WebSocket 服务端、捕获底座；发布包不含编辑器代码。
- 发布：WebUI 安装包与游戏内编辑器 jar 独立版本、独立发布；每次注明 `for <主模组版本>`。
