# 帧捕获底座（预览 / 游戏内编辑器共用）

> 状态：J-2 已实现 CPU 读回；J-3 尺寸参数化与引用计数；J-4 收口为 `CaptureHub`（PBO 三缓冲、采样无上限、预览固定 1920×1080@60）；GPU 直连未做（移交 Z 轮，见 `I-BACKLOG.md` J4-O4）
> 范围：捕获点、输出尺寸、像素格式、帧时间戳、消费者接口；预览与游戏内编辑器共用的捕获层
> 关联：`preview-stream.md`、`../F-playback/multi-camera-rendering.md`、`../Z-editor/README.md` §8.3.1

## 一、摘要

捕获层只做一件事：在固定时机产出一帧（像素 + PTS + 尺寸），消费者决定怎么用。J-4 起只有一个入口 `media.capture.CaptureHub`：

- 捕获点 `hud`：世界 + HUD + 覆盖层 + lane 合成 + 调色，不含任何 Screen UI；
- 预览固定 1920×1080@60，采样无上限（每个渲染帧都采），发送端按 60fps 节流。

## 二、为什么做

### 2.1 问题

- 旧 `WebFrameStreamer` 把捕获、缩放、发送写在一起，固定 1280×720、无 PTS、无编码、串行写会话。
- 预览与游戏内编辑器如果各自实现捕获，会重复处理尺寸、翻转、像素格式、队列与线程边界。
- 两套捕获对“同一帧”的理解可能不同。

### 2.2 目标

- 一个捕获层，预览与游戏内编辑器共用同一帧。
- 输出固定 1920×1080@60，不受窗口缩放影响。
- 每帧带 PTS 与 frameId；消费者按时间处理。
- 采样无上限；背压由消费者声明，渲染线程不被阻塞。
- 线程边界固定：捕获/读回在渲染线程，编码/网络在工作线程。

### 2.3 非目标

- 不做编码；编码归消费者。
- 不做文件写出。
- 不改变合成路径本身（lane/覆盖层/调色）。

## 三、方案

### 3.1 捕获点

| 捕获点 | 内容 | 用途 |
|---|---|---|
| `world` | 世界渲染结果：lane 合成 + 覆盖层，不含 HUD / Screen UI | 可选：只要干净世界画面 |
| `hud`（当前唯一） | 世界 + HUD + 覆盖层 + lane 合成 + 调色；**不含任何 Screen UI** | 预览、游戏内编辑器 |
| `final` | 主 framebuffer，含 Screen UI | 仅调试 |

`hud` 点口径（用户 2026-11-08 裁决，沿用 Z-editor §8.3.1）：

- 原版 HUD 在 Screen 之前绘制；`!hideGui || screen != null` 时 HUD 照常渲染。
- 消费者在自己的 `render` 开头、画自己的 UI 之前提交捕获。
- 因此 `hud` = 世界 + HUD，天然不含编辑器 UI；不新增 `include_hud` 字段，HUD 层放行由脚本 `screen_layers` 决定。

### 3.2 尺寸与格式

- 输出固定 1920×1080@60（2026-11-09 用户裁决：预览只传 1080p60）。
- 像素格式固定 RGBA8，行序自顶向下（捕获层内完成翻转）。
- 尺寸在 `CaptureHub` 规格变化时重建；窗口缩放不影响输出。

### 3.3 采样与时间戳

- 每帧带 PTS：单调时间 `System.nanoTime()`。
- **采样无上限**：未暂停时每个渲染帧都交给 `CaptureHub`；预览消费者在发送端按 60fps 节流。
- 捕获层只负责“这一帧是什么时候的”，不决定“要不要这一帧”。

### 3.4 产出与背压

- 捕获在渲染线程同步产出，`CaptureHub.Consumer` 同线程回调；捕获层不持跨线程队列。
- 缓冲池 6 个 `byte[]`；`CapturedFrame` 用引用计数在消费者之间共享；池空丢帧并计数，不阻塞渲染线程。
- 跨线程消费者自己持有界队列；预览丢最旧帧并计数。

## 四、技术细节

### 4.1 核心模型

| 对象 | 职责 |
|---|---|
| `CaptureHub` | 唯一捕获入口：按需捕获、PBO 三缓冲、多消费者分发、规格切换 |
| 捕获规格 | 固定 1920×1080@60 |
| 捕获帧 | 像素缓冲、宽高、PTS、frameId |
| 消费者 | `needsFrame` / `onFrame` / `captureSpec` |

### 4.2 契约

- **创建**：渲染线程通过 `CaptureHub.register(consumer)` 注册；重复注册忽略。
- **捕获**：`GameRenderer.render` 的 `Gui.render(...)` 返回之后调用 `CaptureHub.onHudRendered`。
- **PBO**：3 个槽；第 N 帧写 `pbo[write]`，映射并交付两帧前的 `pbo[(write+1)%3]`；首两帧只写不读，稳态延迟 2 帧。
- **尺寸**：固定 1920×1080@60；规格变化时重建 FBO/PBO/池并通知消费者。
- **销毁**：关屏 / 世界退出时消费者注销；`CaptureHub.close` 释放 FBO/PBO/池。
- **线程**：捕获与像素提交在渲染线程；编码 / 网络在工作线程；帧缓冲不跨线程共享可变内容。
- **所有权**：一帧只归一个消费者；消费者归还缓冲后才可复用。
- **同进程消费者（游戏内附属模组）**：暴露捕获 FBO / 纹理 + 帧回调，GPU 内直接采样或 blit，不强制读回 CPU；**未实现（归属 Z 轮，`I-BACKLOG.md` J4-O4）**。

### 4.3 数据形态

- 帧：连续 RGBA8 缓冲，1920×1080，行序自顶向下。
- 时间：PTS + frameId；PTS 基准在会话创建时确定。
- 池：6 个缓冲，容量固定；池空丢帧计数。

### 4.4 边界

- 不做编码、不做网络、不做文件。
- 不改渲染/合成路径；捕获只读当前 framebuffer，不介入 lane/覆盖层/调色。

## 五、为什么不选别的

| 备选方案 | 做法 | 代价 | 为什么没选 |
|---|---|---|---|
| 预览与编辑器各自捕获 | 两套读回/缩放/队列 | 重复代码、帧不一致、线程边界各自为政 | 统一 `CaptureHub` |
| 只读主 framebuffer | 所见即所得 | 含所有 Screen UI、受窗口缩放 | 用 `hud` 捕获点（HUD 后、Screen UI 前） |
| 捕获层决定采样与丢帧 | 捕获时按固定规则筛帧 | 预览节奏与编辑器不同 | 采样/背压由消费者声明 |
| 同步 `glReadPixels` | 每帧直接读回 | GPU 等待，帧率下降 | PBO 三缓冲异步读回 |

**本方案的缺点**：

- 每渲染帧一次 1080p 读回 + 拷贝 + 翻转，采样无上限时仍有固定开销。
- `hud` 点依赖调用顺序；调用点写错会把编辑器 UI 录进去。

## 六、实现结果

状态：CPU 读回 + PBO 三缓冲已实现（J-4）；GPU 直连未做（移交 Z 轮）。

- 捕获层：`media.capture.CaptureHub` / `CapturedFrame`；`FrameCapture` / `FrameSink` 已删除。
- 捕获点：`GameRendererMixin` 在 `Gui.render` 返回之后调用 `CaptureHub.onHudRendered`；原版 HUD 已画完 → 含 HUD、不含 Screen UI。
- 输出契约：固定 1920×1080@60；RGBA8；行序自顶向下；PTS = `System.nanoTime()`；frameId 每次捕获自增。
- 产出：PBO 三缓冲异步读回；池 6 + `CapturedFrame.retain/release`；池空丢帧计数；消费者非阻塞。
- 预览消费者：`PreviewStreamer` 实现 `CaptureHub.Consumer`；发送端按 60fps 节流，帧格式 18B 头。
- 同进程 GPU 消费者接口：**未实现（移交 Z 轮，见 `I-BACKLOG.md` J4-O4）**。

## 七、给 Z 轮铺路（J 轮已实现 + 移交项）

- **捕获点 `hud`**：游戏内编辑器的 Screen 在 `render` 开头、画自己 UI 之前调用捕获，与 WebUI 预览一致（J-4 已实现捕获层，Z 轮接入调用点）。
- **同进程消费者接口**：暴露捕获 FBO / 纹理 id + 帧回调；附属模组直接 GPU 采样 / blit，不强制读回 CPU。**未实现（归属 Z 轮，`I-BACKLOG.md` J4-O4）**。
- **尺寸参数化**：编辑器 / 附属模组传尺寸，捕获层不写死尺寸。
- **信号语义复用**：游戏内编辑器与 WebUI 共用 Z-editor §8.3.2 的 `script.*` / `editor.*` / `playback.state`。
- **编辑器开关**（Z-editor §8.2）不属于 J 轮。
