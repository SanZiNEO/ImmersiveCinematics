# 帧捕获底座（预览与导出共用）

> 状态：J-2 已实现 CPU 读回路径；J-3 已实现尺寸参数化与缓冲池/引用计数；GPU 直连未做（J 轮收尾）
> 范围：捕获点、输出尺寸、像素格式、帧时间戳、消费者接口；预览 / 导出 / 游戏内编辑器共用的捕获层
> 关联：`preview-stream.md`、`export.md`、`../F-playback/multi-camera-rendering.md`、`../Z-editor/README.md` §8.3.1

## 一、摘要

现有预览通道已经是一套“逐帧捕获 + 输出”的链路，只是输出的是固定 1280×720 的原始 RGBA。把捕获与输出拆开：捕获层产出一帧（像素 + 时间戳 + 尺寸），消费者决定怎么用——预览编码成本地 WebSocket 帧流，导出编码成文件，游戏内编辑器直接拿 GPU 资源。预览和导出不再各自实现捕获。

## 二、为什么做

### 2.1 问题

- `WebFrameStreamer` 把捕获、缩放、发送写在一起，固定 1280×720、无 PTS、无编码、串行写会话。
- 导出如果另起一套捕获，会重复处理尺寸、翻转、像素格式、队列与线程边界。
- 两套捕获对“同一帧”的理解可能不同，预览看到的和导出的可能不一致。

### 2.2 目标

- 一个捕获层，预览与导出共用；同一脚本、同一时刻，两边拿到同一帧。
- 输出尺寸可配，不受窗口缩放影响；支持固定目标尺寸。
- 每帧带 PTS 与 frameId；消费者按时间处理，不靠到达顺序。
- 消费者侧队列有界；背压策略由消费者声明（预览可丢帧，导出按目标帧率采样）。
- 线程边界固定：捕获/上传在渲染线程，编码/IO 在工作线程。

### 2.3 非目标

- 不做编码；编码归各消费者。
- 不做网络/文件写入；那属于 sink。
- 不改变合成路径本身（lane/覆盖层/调色）。

## 三、方案

### 3.1 捕获点

捕获点是**帧内时机**，不是“两种互斥的捕获源”。三个点，按消费者选：

| 捕获点 | 内容 | 用途 |
|---|---|---|
| `world` | 世界渲染结果：lane 合成 + 覆盖层，不含 HUD / 任何 Screen UI | 可选：只要干净世界画面的成片 |
| `hud`（默认） | 世界 + HUD + 覆盖层 + lane 合成 + 调色；**不含任何 Screen UI** | 预览、导出、游戏内编辑器（三者共用） |
| `final` | 主 framebuffer，含 Screen UI | 仅调试 |

`hud` 点的实现口径（用户 2026-11-08 裁决，沿用 Z-editor §8.3.1）：

- 原版 HUD 在 Screen 之前绘制；`!hideGui || screen != null` 时 HUD 照常渲染。
- 消费者（`WebPreviewScreen` / 游戏内编辑器的 Screen）在自己的 `render` 开头、**画自己的 UI 之前**提交捕获。
- 因此 `hud` = 世界 + HUD，天然不含编辑器 UI；**不新增 `include_hud` 字段**，HUD 层放行由脚本 `screen_layers` 决定。
- 预览与导出是同一捕获点：两者都是“播放脚本时编辑器看到的画面”，导出发生在编辑器模式下，正常游戏不导出。

### 3.2 尺寸与格式

- 捕获尺寸是**消费者参数**：编辑器配置多少就是多少；`FrameCapture.create(w,h)` 不写死。
- J-3 现状：WebUI 预览三档 `original`（默认，窗口 framebuffer，resize 重建）/ `720p` / `1080p`，由 `editor.previewConfig` 下发；`original` 在无 ffmpeg 时自动封顶 1280×720（RGBA 回退带宽保护）。
- 像素格式固定一种（RGBA8），行序约定一次；消费者不得各自假设。
- 尺寸在捕获会话创建时固定；会话期间窗口变化不影响输出（需要新尺寸就重建会话）。

### 3.3 采样与时间戳

- 每帧带 PTS：单调时间 `System.nanoTime()`（J-2 现状，也是捕获层唯一时间口径）。
- 脚本局部时间不塞进捕获帧：导出消费者按脚本局部时间累加 `1/fps` 采样，并维护「捕获 PTS → 脚本局部时间」映射（见 `export.md` §3.2）。
- 采样策略由消费者声明：
  - 预览：跟随渲染帧，允许丢帧；
  - 导出：按目标 fps 采样，按脚本时间累加取帧。
- 捕获层只负责“这一帧是什么时候的”，不决定“要不要这一帧”。

### 3.4 产出与背压

- J-3 现状：捕获在渲染线程同步产出，`FrameSink` 同线程回调；捕获层不持跨线程队列。捕获层内部维护 3 个 `byte[]` 缓冲池，`CapturedFrame` 用引用计数（`retain/release`）在消费者之间共享；池被下游占满时丢弃本帧并计数（`FrameCapture.droppedFrames()`），不阻塞渲染线程。
- 跨线程消费者（编码 / 文件写入）自己持有界队列；预览丢最旧帧并计数，导出阻塞提交（导出不随便丢）。
- 背压策略由消费者声明，捕获层不硬编码。

## 四、技术细节

### 4.1 核心模型

| 对象 | 职责 |
|---|---|
| 捕获会话 | 捕获点、尺寸、像素格式、PTS 基准、生命周期 |
| 捕获帧 | 像素缓冲、宽高、PTS、frameId |
| 帧队列（消费者侧） | 有界缓冲、满时策略（丢/阻塞）、计数 |
| 消费者 | 声明采样策略与背压策略；消费帧 |

### 4.2 契约

- **创建**：预览 / 导出 / 游戏内编辑器各自创建捕获会话；捕获点（默认 `hud`）、尺寸、像素格式是会话参数。
- **尺寸**：由消费者给（编辑器配置）。WebUI 预览默认 1280×720；导出按目标分辨率；无 ffmpeg 时原始画面按带宽降尺寸。`FrameCapture` 本身不写死尺寸。
- **销毁**：会话结束 / 取消 / 失败时释放缓冲与 FBO；不留下悬挂消费者。
- **线程**：捕获与像素提交在渲染线程；编码 / IO 在工作线程；帧缓冲不跨线程共享可变内容。
- **所有权**：一帧只归一个消费者；消费者归还缓冲后才可复用。
- **一致性**：同一捕获点、同一时刻，预览与导出拿到相同像素内容（含脚本放行的 HUD）。
- **同进程消费者（游戏内附属模组）**：暴露捕获 FBO / 纹理 + 帧回调，GPU 内直接采样或 blit，不强制读回 CPU；接口按“附属模组怎么方便怎么写”设计，不引入跨进程协议。
- **跨进程消费者（WebUI）**：本地通信；有 ffmpeg 走编码流，无 ffmpeg 走原始 RGBA。
- **同时开启**：同尺寸可共享会话；不同尺寸各自独立会话，互不阻塞。

### 4.3 数据形态

- 帧：连续像素缓冲，宽高固定，格式单一。
- 时间：PTS + frameId；PTS 基准在会话创建时确定。
- 队列：按帧计数，容量固定；丢帧计数单独记录。

### 4.4 边界

- 不做编码、不做网络、不做文件。
- 不改渲染/合成路径；捕获只读当前 framebuffer，不介入 lane/覆盖层/调色。
- 不定义预览/导出的具体参数；那属于各自消费者。

## 五、为什么不选别的

| 备选方案 | 做法 | 代价 | 为什么没选 |
|---|---|---|---|
| 预览与导出各自捕获 | 两套读回/缩放/队列 | 重复代码、帧不一致、线程边界各自为政 | 统一捕获层，消费者只决定去向 |
| 只读主 framebuffer | 所见即所得 | 含所有 Screen UI、受窗口缩放 | 默认用 `hud` 捕获点（HUD 后、Screen UI 前） |
| 捕获层决定采样与丢帧 | 捕获时按固定规则筛帧 | 预览和导出节奏不同，无法共用 | 采样/背压由消费者声明 |

**本方案的缺点**：

- 捕获层要同时满足“可丢帧”和“不可丢帧”两种节奏，背压契约要写清楚。
- `hud` 点的正确性依赖屏幕在 HUD 之后、自己 UI 之前调用捕获；调用点写错就会把编辑器 UI 录进去。
- 统一像素格式后，某些消费者可能需要额外翻转/转换。

## 六、实现结果

状态：CPU 读回路径已实现（2026-11-08，J-2）；J-3 已实现尺寸参数化、缓冲池与引用计数；GPU 直连未做。

- 捕获层：`media.capture.FrameCapture` / `CapturedFrame` / `FrameSink`。
- 捕获点：`hud`。`WebPreviewScreen.render` 开头、画飞控 HUD 之前提交捕获；原版 HUD 在 Screen 之前已画完 → 含 HUD、不含 `WebPreviewScreen` 自己的 UI。
- 输出契约：尺寸是 `FrameCapture.create(w,h)` 参数；WebUI 预览三档 `original/720p/1080p`（默认 original，无 ffmpeg 时 original 封顶 720p）；RGBA8；行序自顶向下（捕获层内完成翻转）；PTS = `System.nanoTime()`；frameId 每次捕获自增。
- 产出：同步回调 `FrameSink`；捕获层不持队列；3 缓冲池 + `CapturedFrame.retain/release`（池空丢帧计数）；预览消费者每会话编码器/发送队列。
- 预览消费者：`PreviewStreamer` 实现 `FrameSink`，帧格式 18B 头（type/flags/frameId/PTS/宽/高）+ payload；`WebFrameStreamer` 已删除。
- 同进程 GPU 消费者接口：**未实现**（J 轮铺路项，见 §七）。当前只有 CPU 读回路径。
- 逐位一致：同一读回字节经旧路径（逐行拷贝翻转 + 打包）与新路径（`FrameCapture.flipRows` + 打包）输出逐位相同（无头探针 10/10，含 1280×720）。

## 七、给 Z 轮铺路（J 轮必须提前实现）

- **捕获点 `hud`**：游戏内编辑器的 Screen 在 `render` 开头、画自己 UI 之前调用捕获，与 WebUI 预览一致。
- **同进程消费者接口**：暴露捕获 FBO / 纹理 id + 帧回调；附属模组直接 GPU 采样 / blit，不强制读回 CPU。附属模组是自研，接口以“好写”为准，不搞跨进程协议。
- **尺寸参数化**：编辑器 / 附属模组传尺寸，捕获层不写死 720p。
- **信号语义复用**：游戏内编辑器与 WebUI 共用 Z-editor §8.3.2 的 `script.*` / `editor.*` / `playback.state`，J 轮不另造协议。
- **编辑器开关**（Z-editor §8.2）不属于 J 轮。
