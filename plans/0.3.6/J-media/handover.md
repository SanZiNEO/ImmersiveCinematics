## 一、B18 ④ 过渡「打断」实机验证

### 1.1 语义基准（用户 2026-11-06 确认）

- 过渡是 **morph**：两个片段视为无间隔，过渡窗口 = 交界 **± maxDuration/2**。
  例：morph 5s → 交界前后各 2.5s；**上一片段的第 2.5s 位置 → 下一片段的第 2.5s** 平滑过渡。
- 两侧各按**自己的执行位置**取实际状态（含各自片段效果、motion/breath 的当帧推进），**不取末帧/首帧**。
- 在窗口内被新片段打断：默认 `blend` = 从**当前实际混合状态**继续混到新目标；`snap` = 直接切到新目标。默认 `blend` 为 2026-10-11 用户拍板。

### 1.2 要验什么

1. 打断帧**单调、无跳变**（不出现「弹回上一片段末帧再开始」）。
2. **无双重混合**（新旧两段不同时叠加）。
3. 窗口按打断时刻**重算后时长正确**。
4. 与 `snap` 档对照应有**可见差异**（证明 `blend` 分支真的在走）。

### 1.3 实现口径（读码，`CameraTransitionLayer.interrupt`）

- `BLEND`（缺省）：`frozenFrom.copyFrom(lastOutput)` → 当前混合中间态成为新 A 侧；`startTime = now`、`centered = false`、曲线重新实例化 → **逐位连续、时长重新起算**。
- `SNAP`：新窗口按新交界居中，`snapped = true` → 本窗口内恒取 B 侧。
- 结算：`settle()` 记录 `settledBoundary`；同一交界不重开，更早的交界忽略。
- 非单调时间轴（宏观循环折返 / seek）→ `reset()` 自愈。

### 1.4 现有证据

- 探针 51/51：含「打断实际触发」「窗口三处收敛单源」「macro-loop 圈复位双保险」「零分配」。
- 未改路径 2403 行逐字节基线（raw-bits 对拍）。
- **缺**：实机帧。

### 1.5 验收方式

- fixture：`cinematics/0.3.6/tests/camera/test_camera_transition_b18_a.json`、`test_camera_transition_b18_b.json`、`test_camera_transition_params.json`。
- 记录：逐帧六参数（位置 / yaw / pitch / roll / fov / zoom）+ 判别帧截图（`ic shot`，游戏内帧缓冲）。
- 通过标准：无跳变帧、无双重混合、窗口时长符合重算值、`snap` 对照可见差异。

## 二、B18 ⑤ 过渡「链式」实机验证

### 2.1 语义基准

- A→B→C 连续过渡：第二段从 **B 的实际状态**起步，不重置、不取 B 的静态末帧、不把两段窗口叠成一次混合。
- 用户判断（2026-11-06）：**按上述 morph 语义，理论上不应有问题**；实机确认即可。

### 2.2 实现口径（读码，`CameraTransitionLayer`）

- 驱动入口 `blendInto(now, boundary, spec, from, to, out)`：**只要当前有过渡在跑、且交界变了**，就进 `interrupt(...)`；只有「不在过渡中且新交界大于已结算交界」才 `begin(...)`。
- 所以**链式 = 一串打断**，不是「排队两段过渡」：
  - `TransitionInterrupt.BLEND`（缺省）：把**当前输出**冻结成新的 A 侧（`frozenFrom = lastOutput`），`startTime = now`，**时长从打断时刻重新起算且不再以交界居中**（`centered = false`）→ 逐位连续、无跳变。
  - `TransitionInterrupt.SNAP`：窗口按新交界重新居中，窗口内恒取 B 侧。
- `settle()` 记录 `settledBoundary`，同一交界不重开、更早的交界忽略（防重复结算）。
- 时间轴非单调（宏观循环折返 / seek）→ `reset()` 自愈：清空过渡与结算记录，按新交界重新开始。

> 实机要特别看的一点：链式里第二段的窗口是 `[now, now + maxDuration]`（不居中），与「单段过渡居中」不同；这是设计使然，不是 bug——但如果观感上觉得第二段偏短，就是这里。

### 2.3 现有证据

- 同 ①（探针 51/51 + 逐字节基线）。**缺**实机帧。

### 2.4 验收方式

- 与 ① 在**同一次装置**内完成（增量成本很小）。
- 记录三段衔接处的逐帧六参数；通过标准：衔接点无跳变、第二段起点等于 B 的当帧实际状态。

## 三、B19 迟滞观感（人眼判定）

### 3.1 为什么必须人看

headless 只能证明「帧率无关」与「数学正确」（已做：四档 dt、三型对照、闭式步进 vs 数值积分残差 1e-9~1e-7）。**观感**（跟手度、过冲、拖影、与关键帧折点的交互）测不出来，必须人眼。

### 3.2 方法：经典四象限对照（用户 2026-11-06 指定）

- 同屏四条独立 CAMERA 轨（现有四相机轨能力，`cinematics/release/quadrant.json` 可作骨架），四象限各一台相机、同一运动轨迹。
- **一个象限：A→B 无迟滞**（直线/关键帧直接运动）= 对照组。
- **其余三个象限：不同对象分别挂迟滞**（建议 `exponential_smooth` / `spring` / `inertia` 各一型），轨迹与对照组一致。
- 同屏对比：哪一型更接近预期、过冲与滞后是否可接受。

### 3.3 验收方式

- 四象限同屏录制/截图 + 人眼结论（逐型一句话），记录帧率档位（建议 60 / 120 / 解锁三档各看一次）。
- 通过标准：结论可复述、可对照（不是「看起来还行」）。

## 四、C-pause 实机复验

### 4.1 背景

`pause` 已从「冻结时钟」改为**执行状态暂停**：保持内容位置 `(片段, 片段内偏移)` 并上报服务端，恢复从该位置续；服务端 EVENT 时间线按上报位置推进。改动落地时按用户指示**未做测试**，只有 `compileJava` + icv 构建面校验。

### 4.2 要验什么

播到含 EVENT 的片段中途 `pause` → 等 3s → `resume`：

1. 内容位置 `(片段, 片段内偏移)` 保持不变；
2. 服务端 EVENT **不重复触发、不丢触发**；
3. 恢复后内容继续推进（不是重头开始）；
4. `cinematics/0.3.6/tests/rules/test_rules_actions.json` 的 clip3 **不再卡死**（历史 bug）。

### 4.3 验收方式

- 实机 + 日志（`C2SScriptPausePacket` 的位置字段、服务端 `timelineAnchorSeconds` 重定基准、EVENT 触发计数）。
- 通过标准：四条逐项有日志/帧证据。

## 五、F 轮失败处理 P1 / P2

### 5.1 原则（用户 2026-11-06）

1. **有什么放什么**：失败不改变「按脚本数据执行」的语义，不做智能补偿、不猜作者意图。
2. **失败不导致游戏崩溃**：边界捕获 + 降级；单条坏脚本 / 坏关键帧 / 坏图层不得打崩客户端或服务端。
3. **日志定位**：失败在视觉上很容易看出来，所以**原因必须写进日志**（带 `scriptId` / `instanceId` / 层级 / 字段路径 / 限频），靠日志定位为什么失败。

### 5.2 范围

- `F-playback/failure-handling-audit.md` 的 **P1 / P2 批**（约 37 条）；P0（23 条）已在 `4eb65b7` 落地。
- 典型：`OverlayManager.layer.tick` 无捕获、`GameRendererMixin` 调试捕获无捕获、`ScriptEventManager.onServerTick` 遍历 playback 无按实例隔离。

### 5.3 验收方式

- 逐条改造 + 一次「坏数据注入」冒烟：坏 keyframe / 坏命令 / 坏图层 → 不崩，日志有可定位记录。
- 通过标准：注入项逐条有日志行，进程存活，其余实例/轨道继续运行。
