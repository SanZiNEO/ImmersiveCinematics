# 编辑器预览编码流（网络 sink）

> 状态：未实现
> 范围：捕获帧的编码、每会话有界队列、PTS、关键帧、慢客户端降级；只负责网络输出
> 关联：`capture.md`（共用捕获层）、`export.md`（同一捕获层的文件 sink）、`docs/modules/editor.md`

## 一、摘要

预览消费者从共用捕获层取帧，编码成 H.264（ffmpeg 不可用时 MJPEG），按会话有界队列发送；每帧带 PTS，前端按时间抖动缓冲；慢客户端丢最旧帧并降级，不阻塞其他会话。

## 二、为什么做

### 2.1 问题

- 现有预览只发原始 RGBA，720p@60fps 约 221 MB/s，远程不可用。
- 帧头只有 16 bit frameId，没有 PTS；前端只能按到达顺序硬播。
- `broadcastBinary` 串行同步写 session，慢客户端会阻塞整条流。

### 2.2 目标

- 预览走编码帧，带宽随分辨率/帧率可控；分辨率与帧率可配，不再受现有 720p/60fps 原始 RGBA 实现的限制。
- 每帧带 PTS，前端按时间抖动缓冲。
- 每会话独立有界队列；慢客户端丢帧/降级，不影响其他会话。
- 新会话从关键帧开始；暂停时停止编码，恢复时重新取关键帧。

### 2.3 非目标

- 不做捕获与尺寸控制（归 `capture.md`）。
- 不做远程媒体文件传输（归 `transport.md`）。
- 不做直播/推流协议（HLS/DASH/RTMP）。
- 不把音频混进帧流。

## 三、方案

### 3.1 输入

- 从共用捕获层取帧；采样策略为“跟随渲染帧、允许丢帧”。
- 捕获源默认合成 FBO；需要所见即所得时切窗口源。

### 3.2 编码

- 首选 H.264（ffmpeg 编码），分片发送；ffmpeg 不可用时退回 JPEG/MJPEG。
- 编码器按会话隔离，不跨会话共享编码状态。
- 编码在工作线程；渲染线程只提交捕获帧。

### 3.3 会话与背压

- 每个 WebSocket 会话一个有界发送队列；队列满时丢最旧帧并计数。
- 慢客户端降级为低分辨率/低帧率；不阻塞其他会话。
- 新会话/恢复播放时先发关键帧；关键帧间隔可配。

### 3.4 暂停与恢复

- 预览暂停时停止编码；恢复时从当前播放头重新取关键帧。
- 会话断开时释放编码器与队列，不留下编码进程。

## 四、技术细节

### 4.1 核心模型

| 对象 | 职责 |
|---|---|
| 预览编码器 | 捕获帧 → 编码分片；每流/每会话一份 |
| 会话队列 | 有界发送队列、丢帧计数、降级状态 |
| 帧头 | PTS、frameId、关键帧标记 |

### 4.2 契约

- **创建**：会话建立时创建编码器与队列；首帧必须是关键帧。
- **销毁**：会话断开时释放编码器与队列；不留下编码进程。
- **背压**：队列有界；满则丢最旧帧并计数，不无界增长。
- **降级**：连续丢帧超过阈值时降低分辨率/帧率；恢复后不自动升档，由会话重建或显式恢复。
- **线程**：编码在工作线程；解码/渲染线程不等待网络写入。

### 4.3 数据形态

- 编码分片：必须带帧边界与关键帧标记；容器/编码格式由实现定。
- 帧头：PTS、frameId、关键帧布尔。
- 队列：按帧或按字节计数，二者取一，不混用。

### 4.4 边界

- 不改脚本字段；预览是编辑器/运行时通道。
- 不传原始 RGBA 给远程客户端。
- 不与 `transport.md` 的分片缓存混用：预览是流，媒体是文件。
- 不负责捕获尺寸与像素格式（归 `capture.md`）。

## 五、为什么不选别的

| 备选方案 | 做法 | 代价 | 为什么没选 |
|---|---|---|---|
| 继续发原始 RGBA | 不改协议 | 720p@60fps 约 221 MB/s，远程不可用 | 编码 + PTS + 每会话背压 |
| 远程实时传帧 | 服务端编码每帧下发 | 带宽/延迟/服务端 CPU 不可控 | 远程传文件分片，本地解码 |
| 无界发送队列 | 尽量不丢帧 | 慢客户端拖死内存与其他会话 | 有界队列 + 丢帧 + 降级 |

**本方案的缺点**：

- 预览编码增加 ffmpeg 进程与前端解码依赖。
- MJPEG 回退的带宽仍明显高于 H.264。
- 丢帧降级会改变预览观感，作者可能误判画面。
