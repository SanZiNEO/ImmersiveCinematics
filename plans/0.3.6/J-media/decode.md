# 解码链路（ffmpeg 进程 → 纹理）

> 状态：未实现
> 范围：外部 ffmpeg 解码进程、rawvideo 管道、有界帧队列、PTS、双缓冲纹理上传、seek 重启
> 关联：`playback.md`、`degrade.md`、`transport.md`、`../F-playback/multi-camera-rendering.md`

## 一、摘要

每份活跃视频图层对应一个外部 ffmpeg 进程：输出固定尺寸的 RGBA rawvideo 帧，经有界队列送到渲染线程，上传到两张预分配纹理之一。解码与渲染线程分离，队列满时阻塞解码线程而不是渲染线程。

## 二、为什么做

### 2.1 问题

- 全仓没有解码器；`TextureManager` 只接受 PNG，`AudioReader` 只接受 WAV/OGG。
- 没有按时间取帧的链路；现有 GIF 是整段拆帧。
- 渲染线程不能被 IO/解码阻塞，否则帧率抖动。

### 2.2 目标

- 帧从文件到纹理的路径固定、可观测：进程输出 → 队列 → 上传。
- 解码与渲染线程不共享可变帧缓冲。
- seek 有明确的重启语义，不出现越界读到旧帧。
- 队列有界，内存不随时间增长。

### 2.3 非目标

- 不做编码/导出（预览编码见 `preview-stream.md`）。
- 不内嵌解码器、不做 JNI、不打包 ffmpeg。
- 不做“从当前位置快进解码”的 seek 优化。

## 三、方案

### 3.1 解码流程

1. 探测元数据：宽高、帧率、时长、像素格式；结果缓存，避免每次播放重新探测。
2. 启动 ffmpeg：输出 `rawvideo`、`rgba`、固定 `width * height * 4` 帧；音频 `-an`。
3. 解码线程按帧读取，写入容量 2–4 的有界队列；队列满时阻塞解码线程。
4. 渲染线程按局部时间取目标帧，丢弃过期帧，只上传最新帧；没有新帧时保留上一帧。
5. seek：停当前进程、带超时 join、清空队列、按目标时间重启；重启期间渲染线程继续画最后一帧。
6. 关闭：停解码线程、停进程、清队列、释放纹理；重复关闭幂等。

### 3.2 帧与时间

- 帧时间优先用 ffmpeg 输出 PTS；没有 PTS 时按 `frameIndex / fps` 回退。
- 脚本侧只认片段局部时间；PTS 只用于解码侧选帧。
- 目标帧 = 局部时间 × 帧率；选最接近且不晚于目标的帧。

### 3.3 上传

- 预分配两张 RGBA8 动态纹理，双缓冲交换，避免上传时读到半帧。
- 只在渲染线程上传；解码线程只写队列。
- 上传前按需翻转行序，与现有预览捕获的翻转逻辑统一。

## 四、技术细节

### 4.1 核心模型

| 对象 | 职责 |
|---|---|
| 解码器 | 一个 ffmpeg 进程、stdin 帧读取、有界队列、seek/关闭 |
| 解码帧 | RGBA8 字节、宽高、PTS/帧号 |
| 帧纹理 | 两张预分配纹理，渲染线程上传/交换，关闭释放 |

### 4.2 契约

- **创建**：图层创建时懒启动；首帧请求时探测并起进程。
- **销毁**：先停解码线程，再停进程，最后释放纹理。
- **线程**：解码线程只读进程、写队列；渲染线程只取最新帧、上传纹理。
- **背压**：队列 2–4 帧；满则阻塞解码线程，绝不无界增长。
- **所有权**：一个图层一个解码进程；不跨图层共享进程。

### 4.3 数据形态

- 解码帧：RGBA8，`width * height * 4` 字节，行序与 ffmpeg rawvideo 一致。
- 帧时间：PTS 优先，帧号回退。
- 纹理：RGBA8、双缓冲。
- 进程参数：输出尺寸、像素格式、帧率、`-an`；具体命令由实现定，但不得写进脚本。

### 4.4 边界

- 不碰脚本字段；视频参数不出现在脚本里。
- 不做编码/导出。
- 不把原始帧交给网络层（见 `transport.md`、`preview-stream.md`）。

## 五、为什么不选别的

### 5.1 与 MC 内现有播放项目的路线差异

| 路线 | 代表 | 做法 | 代价 | 本项目为什么不用 |
|---|---|---|---|---|
| LibVLC 进程内原生库 | [WaterMedia](https://github.com/WaterMediaTeam/watermedia) / [watermedia-v3](https://github.com/WaterMediaTeam/watermedia-v3) | JNA 绑 libVLC，原生 binaries 随包分发 | 包体大、natives 平台差异、与光影/渲染线程耦合 | 外部 ffmpeg 进程零打包、崩溃隔离、许可简单；代价是进程管理 |
| FFmpeg JNI/桥 | [FFmpegLib](https://www.curseforge.com/minecraft/mc-mods/ffmpeg-lib) | 把 FFmpeg 库带进模组 | 与 LibVLC 类似的 natives/体积问题 | 不把原生库打进 jar |
| 外部 ffmpeg 进程 | BBS / Replay 导出、本项目 | `ProcessBuilder` + rawvideo 管道 | 需要用户安装 ffmpeg | 选择此路线，见 `degrade.md` |

WaterMedia 证明“MC 内放视频”可行；它解决的是“进程内解码 + 纹理输出”，本项目解决的是“外部进程解码 + 有界队列 + 失败隔离”，两者不冲突，只是取舍不同。

### 5.2 解码内部的备选

| 备选方案 | 做法 | 代价 | 为什么没选 |
|---|---|---|---|
| 渲染线程直接解码 | 每帧读进程/上传 | 渲染线程被 IO/解码阻塞，帧率抖动 | 独立解码线程 + 有界队列 |
| 内嵌解码器 / JNI | 解码器进模组 | 体积、natives、平台差异、崩溃面、许可证 | 外部进程隔离崩溃、零打包 |
| 无界队列 | 解码尽量快 | 内存随时间增长，长视频必爆 | 有界队列 + 背压 |

**本方案的缺点**：

- seek 靠重启进程，延迟和首帧时间取决于文件/关键帧间隔。
- 长 GOP / HEVC / AV1 文件的 seek 首帧可能明显慢。
- 每个图层一个进程，多视频同屏时进程数上升，需要并发上限（见 `degrade.md`）。
