# 0.3.6 目标选择：迟滞（Hysteresis）待办

> 本文只记录 0.3.6 的迟滞设计待办。当前版本（0.3.5 轮次）先落地：
> - 选择器刷新频率（`selector_refresh`）
> - 存活期是否允许换目标（`selector_switch_while_alive`）
> - 目标切换平滑（`selector_switch_smooth`）
>
> 迟滞（避免“距离接近的目标来回 ping-pong”）整体留到 0.3.6 统一处理。

## 背景

`look_at` / `follow` 等使用实体选择器的目标，服务端按 `sort=nearest,limit=1`
返回“当前最近”的目标。1v50 等场景中，多个目标与相机的距离接近且不断变化时，
单纯按最近选会出现频繁切换。

当前已提供：

- `selector_switch_while_alive = false`
  - 当前目标活着就不换；只有目标死亡 / 移除 / 未加载时才重选。
  - 适合“这一段就锁一个目标”的镜头。
- `selector_refresh`
  - 只有 `selector_switch_while_alive = true` 时才真正生效：每隔 N 秒重新求值。
- `selector_switch_smooth`
  - 目标真的切换时，注视点/跟随位置在 N 秒内平滑过渡。

但“允许存活期切换”且多个候选距离接近时，仍会来回切。需要迟滞。

## 迟滞待办

### 候选策略

1. **距离阈值迟滞（margin）**
   - 只有新目标比当前目标近 `margin` 格时才允许切换。
   - 例：`switch_margin = 4.0`，当前目标距离 10，新目标距离 9 → 不换；
     新目标距离 5 → 换。
   - 简单、可预测，适合战斗场景。

2. **距离带迟滞（band）**
   - 当前目标处在“可接受带”内就不换；只有离开该带，或新目标明显更近才换。
   - 比 margin 更稳定，但参数更多。

3. **时间迟滞（cooldown）**
   - 两次切换之间至少间隔 N 秒。
   - 常与 margin 组合使用。

4. **优先级/分数迟滞**
   - 目标带血量、威胁值、分数等优先级；同优先级内才按距离。
   - 需要实体提供可读的分数/NBT，IC 侧只做比较。

5. **目标类型/角色权重**
   - 例如 Boss > 普通单位，近战 > 远程；需要约定 NBT/tag。

### 需要定下来的接口形态

迟滞最终还是落在“选择器策略”上，建议 0.3.6 扩展为：

```json
"selector_policy": {
  "refresh": 1.0,
  "switch_while_alive": true,
  "switch_smooth": 0.3,
  "switch_margin": 4.0,
  "switch_cooldown": 1.5
}
```

即当前三个平铺字段未来可能收拢为 `selector_policy` 对象；
若要兼容现有脚本，则保留平铺字段作为默认值，`selector_policy` 作为角色级覆盖。

### 服务端/客户端职责

- 服务端 `EntitySelectorResolver` 目前按 selector 的 `limit` 返回候选。
- 要支持 margin/band，客户端需要拿到**多个候选**，不能只 `limit=1`。
  0.3.6 需要决定：
  - IC 在解析时覆盖 selector 的 `limit`，强制返回一个候选集；
  - 还是新增一个“返回 N 个候选”的解析模式；
  - 候选集大小上限、排序由谁做（建议服务端按原版 sort 返回，客户端只做迟滞决策）。
- `switch_cooldown` 是纯客户端状态，不需要服务端参与。
- 迟滞决策应放在 `CameraTrackPlayer` 的目标锁层，不进入原版选择器语义。

## 当前不做的事

- 不实现 `switch_margin` / `switch_band` / `switch_cooldown`。
- 不做多候选请求协议。
- 不改变 `EntitySelectorResolver` 的现有 `limit` 行为。

以上留到 0.3.6 统一设计。
